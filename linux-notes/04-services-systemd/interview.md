# Module 04 — Services & systemd
# Technical Interview Questions

## 1. Что такое systemd?

**Ответ:**

systemd — система инициализации и менеджер служб Linux.

Обычно работает как процесс с PID 1.

Основные задачи:
- Запуск и остановка сервисов.
- Управление зависимостями.
- Автоматический запуск сервисов.
- Контроль состояния процессов.
- Автоматический перезапуск сервисов.

---

## 2. Что такое systemd unit?

**Ответ:**

Unit — объект, которым управляет systemd.

Основные типы:

- `.service` — сервисы.
- `.socket` — сокеты и активация сервисов.
- `.target` — группировка units.
- `.timer` — запуск задач по расписанию.
- `.mount` — точки монтирования.
- `.path` — активация при изменениях файловой системы.

---

## 3. Чем отличаются active и enabled?

**Ответ:**

`active` — текущее состояние сервиса.

`enabled` — настройка его автозапуска.

Сервис может быть `active`, но `disabled`.

Например, если его запустили вручную.

---

## 4. Чем отличаются start, restart и reload?

**Ответ:**

- `start` — запускает сервис.
- `restart` — перезапускает сервис.
- `reload` — запрашивает перечитывание конфигурации приложения без полного перезапуска, если сервис поддерживает такую операцию.

Важно: `reload` не предназначен для запуска остановленного сервиса.

---

## 5. Чем отличается daemon-reload от reload?

**Ответ:**

`daemon-reload` заставляет systemd перечитать unit-файлы.

`reload` запрашивает перечитывание конфигурации самого приложения.

Например, после изменения `ExecStart` обычно необходимо выполнить:

```bash
sudo systemctl daemon-reload
# Перечитывает unit-файлы systemd.
```

```bash
sudo systemctl restart app.service
# Перезапускает приложение с новыми параметрами.
```

---

## 6. Чем отличаются enable и start?

**Ответ:**

`enable` настраивает автозапуск сервиса.

`start` запускает сервис прямо сейчас.

Команда:

```bash
sudo systemctl enable --now nginx.service
# Включает автозапуск и сразу запускает nginx.
```

выполняет оба действия.

---

## 7. Чем отличаются disable и mask?

**Ответ:**

`disable` отключает автозапуск, но не запрещает ручной запуск.

`mask` блокирует запуск unit через systemd.

Маскировка обычно реализуется символической ссылкой на `/dev/null`.

---

## 8. Что такое unit-файл?

**Ответ:**

Unit-файл содержит настройки объекта systemd.

Для service unit обычно используются три секции:

- `[Unit]` — описание и зависимости.
- `[Service]` — параметры запуска и работы процесса.
- `[Install]` — настройки подключения unit к другим units при enable.

---

## 9. Что делает ExecStart?

**Ответ:**

`ExecStart` определяет команду запуска приложения.

Пример:

```ini
ExecStart=/usr/bin/python3 /opt/app/app.py
```

Systemd запускает указанную программу при старте сервиса.

---

## 10. Для чего нужны User и Group?

**Ответ:**

Параметры `User=` и `Group=` задают пользователя и основную группу процесса приложения.

Пример:

```ini
User=app
Group=app
```

Это позволяет запускать приложение без root-привилегий.

Пользователь должен иметь необходимые права на исполняемый файл, конфигурацию и рабочие каталоги.

---

## 11. Что такое WorkingDirectory?

**Ответ:**

`WorkingDirectory` задаёт рабочий каталог процесса.

Пример:

```ini
WorkingDirectory=/opt/app
```

Относительные пути, используемые приложением, будут разрешаться относительно этого каталога, если приложение самостоятельно не изменит рабочую директорию.

---

## 12. Чем отличаются Type=simple, Type=forking и Type=oneshot?

**Ответ:**

`simple` — systemd запускает основной процесс и не ждёт отдельного подтверждения готовности приложения.

`forking` — приложение создаёт дочерний процесс, а исходный процесс запуска завершается.

`oneshot` — приложение выполняет определённое действие и завершается.

Для `oneshot` можно использовать:

```ini
RemainAfterExit=yes
```

Тогда после успешного завершения сервис может оставаться в состоянии `active (exited)`.

---

## 13. Что делает Restart=on-failure?

**Ответ:**

Позволяет systemd автоматически перезапускать сервис при определённых видах аварийного завершения.

Например:

```ini
Restart=on-failure
RestartSec=5
```

Если приложение завершится с ошибкой, systemd попытается запустить его повторно после установленной задержки.

---

## 14. Почему Restart=always не перезапускает сервис после systemctl stop?

**Ответ:**

Потому что `systemctl stop` — намеренная остановка сервиса через systemd.

Политика `Restart=always` не отменяет явную команду администратора остановить сервис.

---

## 15. Что такое target?

**Ответ:**

Target — специальный unit, который объединяет другие units и помогает организовать загрузку системы.

Примеры:

- `multi-user.target` — многопользовательский режим.
- `graphical.target` — графический режим.
- `network.target` — этап инициализации сетевого стека.

---

## 16. Чем отличаются Wants и Requires?

**Ответ:**

`Wants=` — слабая зависимость.

Если зависимый unit не запустится, это само по себе не обязательно приведёт к ошибке текущего unit.

`Requires=` — более сильная зависимость.

Если обязательная зависимость не сможет запуститься, запуск текущего unit также может завершиться неуспешно.

Важно: порядок запуска отдельно задаётся через `After=` или `Before=`.

---

## 17. Что делает After=network.target?

**Ответ:**

Определяет порядок запуска относительно `network.target`.

Сам по себе `After=` не запускает указанный target и не гарантирует наличие IP-адреса или доступности сети.

Для ожидания готовности сети может использоваться `network-online.target` с соответствующей службой ожидания.

---

## 18. Что такое socket activation?

**Ответ:**

Это механизм, при котором systemd может запускать сервис при появлении соединения на сокете.

Например, активный `.socket` unit может инициировать запуск соответствующего `.service`.

Поэтому остановленный сервис иногда запускается снова при обращении к нему.

---

## 19. Как посмотреть журнал конкретного сервиса?

**Ответ:**

```bash
journalctl -u nginx.service
# Показывает журнал nginx.service.
```

Последние 50 записей:

```bash
journalctl -u nginx.service -n 50
# Показывает последние 50 записей.
```

Просмотр новых сообщений:

```bash
journalctl -u nginx.service -f
# Следит за новыми сообщениями в реальном времени.
```

---

## 20. Как посмотреть журнал предыдущей загрузки Linux?

**Ответ:**

```bash
journalctl -b -1
# Показывает журнал предыдущей загрузки, если он сохранился.
```

Проверить доступные загрузки:

```bash
journalctl --list-boots
# Показывает список загрузок, доступных в журнале.
```

# Troubleshooting Interview Questions

## 21. Сервис находится в состоянии failed. Что будешь делать?

**Ответ:**

Сначала проверю состояние:

```bash
systemctl status app.service
# Показывает состояние сервиса и последние сообщения.
```

Затем журнал:

```bash
journalctl -u app.service -n 50 --no-pager
# Показывает последние 50 записей журнала.
```

Если причина неочевидна, проверю unit-файл:

```bash
systemctl cat app.service
# Показывает конфигурацию сервиса.
```

Дальнейшие действия зависят от конкретной ошибки.

Не буду сразу менять permissions или многократно перезапускать сервис без понимания причины.

---

## 22. Приложение сообщает Permission denied. Как диагностировать?

**Ответ:**

Проверю:

1. От какого пользователя работает сервис.
2. UID, GID и группы пользователя.
3. Владельца и permissions проблемного файла.
4. Права всех каталогов в пути.
5. ACL, если они используются.

Например:

```bash
namei -l /opt/app/config/settings.conf
# Показывает permissions каждого компонента пути.
```

Важно: для доступа к файлу нужны соответствующие права на сам файл и право прохода `x` через родительские каталоги.

---

## 23. Сервис работает, но сайт возвращает HTTP 502. Что проверишь?

**Ответ:**

Проверю:

- Состояние приложения.
- Журнал приложения.
- Слушает ли приложение ожидаемый порт.
- Отвечает ли локальный HTTP endpoint.
- Конфигурацию reverse proxy.
- Журнал reverse proxy.
- Доступность upstream-приложения со стороны proxy.

Например:

```bash
curl -i http://127.0.0.1:8080/health
# Проверяет локальный HTTP endpoint приложения.
```

Если приложение отвечает локально, но внешний запрос возвращает 502, продолжу диагностику reverse proxy и соединения с upstream.

---

## 24. Почему active (running) не гарантирует работоспособность приложения?

**Ответ:**

Потому что systemd отслеживает состояние сервиса и его процессов, а не всю бизнес-логику приложения.

Например, приложение может:

- Возвращать HTTP 500.
- Не иметь подключения к базе данных.
- Не отвечать на отдельные запросы.
- Быть недоступным через reverse proxy.

Поэтому после восстановления необходимо проверять функциональность приложения.

---

## 25. Почему сервис перестал запускаться после logrotate?

**Ответ:**

Одна из возможных причин — logrotate создал новый файл журнала с неправильным владельцем или permissions.

Например:

```text
-rw-r----- root reporting application.log
```

Если приложение работает от пользователя `reporting`, оно не сможет записывать в этот файл.

Необходимо проверить конфигурацию logrotate, особенно параметр `create`.

Важно исправить не только текущий файл, но и механизм его создания.

---

## 26. Почему журнал сообщает об ошибке конфигурации, хотя файл выглядит правильным?

**Ответ:**

Возможные причины:

- Файл изменили после возникновения ошибки.
- Приложение читает другой конфигурационный файл.
- Ошибка находится в подключаемом конфигурационном файле.
- В файле есть незаметные символы или неправильные отступы.

Следует сопоставить время ошибки со временем изменения файла и проверить фактический путь конфигурации.

---

## 27. Почему не стоит сразу выполнять chmod 777?

**Ответ:**

Потому что это предоставляет всем пользователям широкие права доступа и может создать проблему безопасности.

Правильнее определить, от имени какого пользователя работает приложение и какие именно permissions ему необходимы.

Затем внести минимальное изменение.

---

## 28. Как понять, почему сервис автоматически перезапускается?

**Ответ:**

Проверю:

```bash
systemctl cat app.service
# Показывает конфигурацию unit.
```

Обращу внимание на:

```ini
Restart=
RestartSec=
```

Также проверю журнал:

```bash
journalctl -u app.service -n 50 --no-pager
# Показывает последние события сервиса.
```

Нужно выяснить, почему завершается основной процесс и какая политика перезапуска настроена.

---

## 29. Чем отличается ошибка приложения от ошибки systemd?

**Ответ:**

Systemd может успешно запустить процесс, но само приложение завершится с ошибкой.

Например:

```text
Main process exited, code=exited, status=1/FAILURE
```

Это означает, что процесс приложения завершился с кодом `1`.

Для определения причины нужно изучить журнал приложения.

Также существуют ошибки непосредственно на этапе запуска процесса, например если отсутствует исполняемый файл или systemd не может запустить его из-за прав доступа.

---

## 30. Какой главный принцип troubleshooting?

**Ответ:**

Последовательность:

1. Определить симптомы.
2. Собрать диагностическую информацию.
3. Сформулировать гипотезу.
4. Подтвердить первопричину.
5. Внести минимальное исправление.
6. Проверить восстановление.
7. Убедиться, что проблема не повторится.

Главное правило:

> Diagnose → Identify Root Cause → Apply Minimal Fix → Verify.
