# Module 04 — Services & systemd

## 1. Что такое systemd

`systemd` — система инициализации и менеджер служб в Linux.

После загрузки ядра Linux запускается первый процесс пользовательского пространства, которым в большинстве современных дистрибутивов является `systemd`.

Обычно systemd имеет:

```text
PID = 1
```

Основные задачи systemd:

- Запуск системных сервисов.
- Управление жизненным циклом процессов.
- Автоматический запуск сервисов при загрузке ОС.
- Управление зависимостями между сервисами.
- Автоматический перезапуск неисправных сервисов.
- Управление системными targets.
- Интеграция с журналированием через systemd-journald.

Проверить процесс с PID 1:

```bash
ps -p 1 -o pid,comm,args
# Показывает PID, имя и команду запуска процесса с PID 1.
```

Пример:

```text
PID COMMAND         COMMAND
  1 systemd         /sbin/init
```

Важно: systemd управляет не только сервисами, но и другими системными объектами — units.

---

## 2. Что такое Unit

Unit — объект, которым управляет systemd.

Основные типы units:

| Тип | Назначение |
|---|---|
| `.service` | Управление сервисами |
| `.socket` | Активация сервисов через сокеты |
| `.target` | Группировка units и организация загрузки |
| `.timer` | Запуск задач по расписанию |
| `.mount` | Управление точками монтирования |
| `.automount` | Автоматическое монтирование |
| `.path` | Активация при изменениях файлов или каталогов |

Примеры:

```text
nginx.service
sshd.service
multi-user.target
cups.socket
backup.timer
```

Посмотреть загруженные сервисы:

```bash
systemctl list-units --type=service
# Показывает загруженные service units.
```

Посмотреть все установленные service unit-файлы:

```bash
systemctl list-unit-files --type=service
# Показывает unit-файлы сервисов и их состояние автозапуска.
```

Важно: `list-units` и `list-unit-files` показывают разные вещи.

`list-units` — units, загруженные в менеджер systemd.

`list-unit-files` — unit-файлы, известные systemd, и их состояние установки.

## 3. Состояния сервисов

У systemd есть несколько состояний сервисов.

Основные:

| Состояние | Значение |
|---|---|
| `active (running)` | Сервис работает |
| `active (exited)` | Сервис успешно выполнил действие и считается активным |
| `inactive (dead)` | Сервис не работает |
| `failed` | Сервис завершился с ошибкой |
| `activating` | Сервис запускается |
| `deactivating` | Сервис останавливается |

Проверить состояние:

```bash
systemctl status nginx.service
# Показывает подробное состояние сервиса.
```

Пример:

```text
● nginx.service - A high performance web server
     Loaded: loaded (...; enabled)
     Active: active (running)
   Main PID: 1234 (nginx)
```

Здесь:

- `Loaded` — информация о загрузке unit-файла.
- `enabled` — сервис настроен на автозапуск.
- `Active` — текущее состояние.
- `Main PID` — основной процесс сервиса.

Проверить только активность:

```bash
systemctl is-active nginx.service
# Показывает состояние активности сервиса.
```

Проверить автозапуск:

```bash
systemctl is-enabled nginx.service
# Показывает состояние автозапуска сервиса.
```

Важно:

**Active и enabled — независимые характеристики.**

Сервис может быть:

```text
active + enabled
active + disabled
inactive + enabled
inactive + disabled
```

Например, `disabled` не запрещает ручной запуск сервиса.

## 4. Управление сервисами

Запуск:

```bash
sudo systemctl start nginx.service
# Запускает сервис.
```

Остановка:

```bash
sudo systemctl stop nginx.service
# Останавливает сервис.
```

Перезапуск:

```bash
sudo systemctl restart nginx.service
# Останавливает и заново запускает сервис.
```

Перечитывание конфигурации приложения:

```bash
sudo systemctl reload nginx.service
# Запрашивает перечитывание конфигурации приложения без полного перезапуска.
```

Важно: не каждый сервис поддерживает `reload`.

Если сервис не поддерживает этот механизм, команда может завершиться ошибкой.

Также `reload` обычно применяется к работающим сервисам и не предназначен для запуска остановленного приложения.

## 5. Автозапуск сервисов

Включить автозапуск:

```bash
sudo systemctl enable nginx.service
# Настраивает автоматический запуск сервиса.
```

Отключить автозапуск:

```bash
sudo systemctl disable nginx.service
# Удаляет ссылки автозапуска, созданные через enable.
```

Включить автозапуск и сразу запустить:

```bash
sudo systemctl enable --now nginx.service
# Включает автозапуск и запускает сервис.
```

Отключить автозапуск и остановить:

```bash
sudo systemctl disable --now nginx.service
# Отключает автозапуск и останавливает сервис.
```

Важно:

`enable` не означает `start`.

`disable` не означает `stop`.

### Как работает enable

При выполнении:

```bash
sudo systemctl enable nginx.service
```

systemd обычно создаёт символическую ссылку в каталоге вида:

```text
/etc/systemd/system/multi-user.target.wants/
```

Пример:

```text
nginx.service -> /lib/systemd/system/nginx.service
```

Это позволяет systemd включать сервис в процесс достижения соответствующего target.

Фактическое расположение unit-файла зависит от дистрибутива.

### Mask

`mask` — более сильное ограничение, чем `disable`.

```bash
sudo systemctl mask nginx.service
# Запрещает запуск unit обычными средствами systemd.
```

Обычно создаётся ссылка:

```text
/etc/systemd/system/nginx.service -> /dev/null
```

Снять маскировку:

```bash
sudo systemctl unmask nginx.service
# Убирает запрет на запуск unit.
```

Разница:

- `disable` — отключает автозапуск.
- `mask` — запрещает запуск unit через systemd, пока маскировка действует.

## 6. Unit-файлы

Unit-файл описывает, как systemd должен управлять сервисом.

Основные каталоги:

```text
/etc/systemd/system/
/usr/lib/systemd/system/
/lib/systemd/system/
```

Назначение:

- `/etc/systemd/system/` — локальные unit-файлы и настройки администратора.
- `/usr/lib/systemd/system/` — unit-файлы, поставляемые пакетами.
- `/lib/systemd/system/` — расположение unit-файлов в некоторых дистрибутивах.

Для просмотра unit-файла:

```bash
systemctl cat nginx.service
# Показывает unit-файл и дополнительные drop-in конфигурации.
```

### Пример собственного сервиса

```ini
[Unit]
Description=Payments API
After=network.target

[Service]
Type=simple
User=payments-api
Group=payments
WorkingDirectory=/opt/payments-api
ExecStart=/opt/payments-api/bin/server
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

Unit-файл состоит из нескольких секций.

### [Unit]

Описывает unit и его зависимости.

```ini
[Unit]
Description=Payments API
After=network.target
```

`Description` — описание сервиса.

`After` — задаёт порядок запуска относительно другого unit.

Важно:

**After не означает, что указанный unit обязательно будет запущен.**

Для определения зависимостей используются другие параметры, например `Wants=` и `Requires=`.

### [Service]

Описывает запуск и работу приложения.

```ini
[Service]
Type=simple
User=payments-api
Group=payments
WorkingDirectory=/opt/payments-api
ExecStart=/opt/payments-api/bin/server
Restart=on-failure
RestartSec=5
```

Основные параметры:

| Параметр | Назначение |
|---|---|
| `Type` | Способ определения запуска сервиса |
| `User` | Пользователь, от имени которого запускается процесс |
| `Group` | Основная группа процесса |
| `WorkingDirectory` | Рабочая директория приложения |
| `ExecStart` | Команда запуска приложения |
| `ExecStop` | Команда остановки, если настроена |
| `ExecReload` | Команда перечитывания конфигурации, если настроена |
| `Restart` | Политика автоматического перезапуска |
| `RestartSec` | Задержка перед перезапуском |

Важно: пользователь, указанный в `User=`, должен иметь необходимые права доступа к исполняемому файлу, конфигурации и рабочим каталогам приложения.

### [Install]

Определяет, как unit подключается к другим units при выполнении `systemctl enable`.

```ini
[Install]
WantedBy=multi-user.target
```

При включении автозапуска systemd создаёт соответствующую символическую ссылку.

`WantedBy` не является инструкцией немедленно запустить сервис.

## 7. Типы сервисов

Параметр `Type=` определяет, как systemd отслеживает запуск сервиса.

### Type=simple

```ini
[Service]
Type=simple
ExecStart=/usr/bin/python3 /opt/app/app.py
```

Один из наиболее распространённых типов.

Systemd запускает процесс и считает запуск выполненным сразу после создания процесса, не ожидая подтверждения готовности приложения.

Это означает, что состояние `active` само по себе не гарантирует готовность HTTP API принимать запросы.

### Type=forking

```ini
[Service]
Type=forking
ExecStart=/usr/sbin/example-daemon
PIDFile=/run/example-daemon.pid
```

Используется для приложений, которые при запуске создают дочерний процесс и завершают исходный.

Systemd ожидает завершения первоначального процесса запуска.

`PIDFile` может использоваться для определения основного PID демона.

### Type=oneshot

```ini
[Service]
Type=oneshot
ExecStart=/usr/local/bin/prepare-environment.sh
RemainAfterExit=yes
```

Подходит для задач, которые выполняют действие и завершаются.

Например:

- Подготовка окружения.
- Создание необходимых каталогов.
- Выполнение одноразовой операции при загрузке.

`RemainAfterExit=yes` позволяет сервису оставаться в состоянии `active (exited)` после успешного завершения команды.

Без этого параметра oneshot-сервис обычно переходит в `inactive (dead)`.

## 8. Автоматический перезапуск

Systemd может автоматически перезапускать приложение при завершении процесса.

Пример:

```ini
[Service]
ExecStart=/opt/app/server
Restart=on-failure
RestartSec=5
```

Здесь:

- `Restart=on-failure` — перезапуск при определённых видах аварийного завершения.
- `RestartSec=5` — ожидание пяти секунд перед новой попыткой запуска.

Основные значения:

| Значение | Поведение |
|---|---|
| `no` | Не перезапускать автоматически |
| `on-failure` | Перезапускать при ошибках |
| `on-abnormal` | Перезапускать при определённых аварийных завершениях, например по сигналу |
| `always` | Перезапускать при обычном или аварийном завершении, за исключением специальных случаев |

Важно:

Если выполнить:

```bash
sudo systemctl stop app.service
# Намеренно останавливает сервис через systemd.
```

то даже при `Restart=always` systemd не должен автоматически запускать сервис снова только из-за этой остановки.

### Связь с Linux signals

```bash
kill -15 1234
# Отправляет SIGTERM — запрос на корректное завершение процесса.
```

```bash
kill -9 1234
# Отправляет SIGKILL — принудительное завершение процесса.
```

Если вручную завершить основной процесс сервиса, systemd может запустить новый процесс согласно политике `Restart=`.

Поэтому для штатной остановки сервиса следует использовать `systemctl stop`, а не `kill -9`.

## 9. Targets и зависимости

Target — специальный unit, который используется для группировки других units и организации состояний системы.

Примеры:

```text
multi-user.target
graphical.target
network.target
network-online.target
```

`multi-user.target` обычно соответствует многопользовательскому режиму без обязательного запуска графической среды.

`graphical.target` используется для запуска системы с графической средой.

Посмотреть текущий target по умолчанию:

```bash
systemctl get-default
# Показывает target, используемый по умолчанию при загрузке.
```

Посмотреть зависимости:

```bash
systemctl list-dependencies multi-user.target
# Показывает дерево зависимостей target.
```

### Wants и Requires

`Wants=` — слабая зависимость.

Systemd пытается запустить указанный unit, но его неудачный запуск сам по себе не обязательно приводит к ошибке запуска текущего unit.

`Requires=` — более сильная зависимость.

Используется, когда работа текущего unit зависит от другого unit.

Важно: `Requires=` само по себе не определяет порядок запуска.

Для порядка используется `After=` или `Before=`.

### network.target и network-online.target

`network.target` не гарантирует, что сервер уже получил IP-адрес и сеть полностью готова.

`network-online.target` используется для ожидания готовности сети, если соответствующий механизм ожидания настроен.

## 10. Socket activation

Systemd может запускать сервис при поступлении соединения на сокет.

Для этого используется `.socket` unit.

Пример:

```text
cups.socket
cups.service
```

Socket unit может оставаться активным, даже если сам service unit остановлен.

При поступлении соединения systemd может активировать соответствующий сервис.

Поэтому:

**Остановка или отключение автозапуска service unit не всегда исключает его последующую активацию через socket или path unit.**

Проверить сокеты:

```bash
systemctl list-units --type=socket
# Показывает загруженные socket units.
```

Проверить конкретный socket:

```bash
systemctl status cups.socket
# Показывает состояние socket unit.
```

Дополнительно systemd поддерживает path activation через `.path` units.

## 11. Разница между restart, reload и daemon-reload

Это три разных действия.

### restart

```bash
sudo systemctl restart nginx.service
# Перезапускает приложение.
```

Используется, когда нужно остановить и заново запустить сервис.

Например, после изменения параметров приложения, которые читаются только при запуске.

### reload

```bash
sudo systemctl reload nginx.service
# Запрашивает перечитывание конфигурации приложения.
```

Используется, когда приложение поддерживает перезагрузку конфигурации без полного перезапуска.

### daemon-reload

```bash
sudo systemctl daemon-reload
# Заставляет systemd перечитать unit-файлы и пересобрать зависимости.
```

Используется после изменения unit-файлов systemd.

Например, если изменили:

```ini
ExecStart=/opt/app/new-server
```

то обычно необходимо выполнить:

```bash
sudo systemctl daemon-reload
# Применяет изменения конфигурации systemd.
```

Затем:

```bash
sudo systemctl restart app.service
# Перезапускает приложение с обновлёнными параметрами unit.
```

Главное различие:

| Команда | Что обновляет |
|---|---|
| `restart` | Процесс приложения |
| `reload` | Конфигурацию приложения, если поддерживается |
| `daemon-reload` | Конфигурацию менеджера systemd |

## 12. Журналирование через journalctl

`systemd-journald` собирает системные журналы.

Команда `journalctl` используется для их просмотра.

### Журнал конкретного сервиса

```bash
journalctl -u nginx.service
# Показывает записи журнала, связанные с nginx.service.
```

Последние записи:

```bash
journalctl -u nginx.service -n 50
# Показывает последние 50 записей журнала сервиса.
```

Без постраничного просмотра:

```bash
journalctl -u nginx.service -n 50 --no-pager
# Выводит последние 50 записей непосредственно в терминал.
```

### Просмотр в реальном времени

```bash
journalctl -u nginx.service -f
# Показывает новые записи по мере их появления.
```

Полезно при troubleshooting.

### Фильтрация по времени

```bash
journalctl -u nginx.service --since "1 hour ago"
# Показывает записи сервиса за последний час.
```

```bash
journalctl -u nginx.service \
  --since "2026-10-15 10:00" \
  --until "2026-10-15 11:00"
# Показывает записи сервиса за указанный период.
```

### Журналы загрузок

```bash
journalctl --list-boots
# Показывает загрузки ОС, для которых доступны журналы.
```

```bash
journalctl -b
# Показывает журнал текущей загрузки.
```

```bash
journalctl -b -1
# Показывает журнал предыдущей загрузки, если он сохранился.
```

Важно: доступность журналов предыдущих загрузок зависит от настроек хранения journal.

### Фильтрация по приоритету

```bash
journalctl -p err -b
# Показывает сообщения уровня err и более серьёзные за текущую загрузку.
```

Основные уровни:

```text
0 emerg
1 alert
2 crit
3 err
4 warning
5 notice
6 info
7 debug
```

## 13. Методика troubleshooting systemd

Если сервис не запускается, не следует сразу изменять permissions или многократно выполнять `restart`.

Правильный подход — последовательно собрать информацию.

### Шаг 1. Проверить состояние

```bash
systemctl status app.service
# Показывает состояние сервиса и последние сообщения.
```

Обратить внимание на:

- `Active`
- `Result`
- `Main PID`
- `ExecStart`
- `status=...`
- Последние сообщения журнала.

### Шаг 2. Изучить журнал

```bash
journalctl -u app.service -n 50 --no-pager
# Показывает последние 50 сообщений сервиса.
```

Искать конкретные ошибки:

```text
Permission denied
No such file or directory
Failed to load configuration
Address already in use
Exec format error
```

### Шаг 3. Проверить конфигурацию unit

```bash
systemctl cat app.service
# Показывает unit-файл и дополнительные настройки.
```

Особенно важны:

```ini
User=
Group=
WorkingDirectory=
ExecStart=
Restart=
```

### Шаг 4. Проверить permissions

Если приложение сообщает:

```text
Permission denied
```

нужно определить, от имени какого пользователя оно работает.

```bash
systemctl show app.service -p User -p Group
# Показывает пользователя и группу, указанных для сервиса.
```

Проверить права всех каталогов:

```bash
namei -l /opt/app/config/settings.conf
# Показывает владельцев и permissions всех компонентов пути.
```

При необходимости проверить ACL:

```bash
getfacl /opt/app/config/settings.conf
# Показывает ACL файла.
```

Важно: не нужно сразу использовать `chmod 777`.

Следует определить, какое именно право отсутствует.

### Шаг 5. Проверить конфигурацию приложения

Если журнал указывает на ошибку конфигурации, необходимо проверить соответствующий файл.

Например:

```bash
less /etc/app/config.yaml
# Открывает файл для просмотра.
```

Проверить специальные символы:

```bash
sed -n '1,30l' /etc/app/config.yaml
# Показывает строки 1–30 с визуализацией специальных символов.
```

Проверить время изменения:

```bash
stat /etc/app/config.yaml
# Показывает метаданные файла, включая время последнего изменения.
```

Важно сопоставлять время изменения файла со временем возникновения ошибки.

### Шаг 6. Исправить подтверждённую причину

После определения root cause внести минимально необходимое изменение.

Например:

- Исправить permissions.
- Исправить конфигурацию приложения.
- Исправить unit-файл.
- Исправить настройки logrotate.

### Шаг 7. Проверить результат

После исправления:

```bash
sudo systemctl restart app.service
# Перезапускает приложение.
```

```bash
systemctl status app.service
# Проверяет состояние сервиса.
```

```bash
journalctl -u app.service -n 20 --no-pager
# Проверяет последние сообщения журнала.
```

Если приложение предоставляет HTTP API:

```bash
curl -i http://127.0.0.1:8080/health
# Проверяет HTTP-ответ локального приложения.
```

Важно:

**Состояние `active (running)` не гарантирует, что приложение работает корректно.**

Для веб-приложений дополнительно нужно проверять HTTP-ответы, зависимости и доступность через reverse proxy.

## 14. Типичные ошибки администратора

### Ошибка 1. Путать active и enabled

`active` показывает текущее состояние сервиса.

`enabled` показывает настройку автозапуска.

Это разные характеристики.

### Ошибка 2. Использовать daemon-reload вместо restart

`daemon-reload` перечитывает unit-файлы, но не перезапускает приложения.

### Ошибка 3. Считать disabled запретом на запуск

Disabled-сервис можно запустить вручную.

Кроме того, его могут активировать другие units.

### Ошибка 4. Исправлять Permission denied через chmod 777

Это может создать серьёзную проблему безопасности.

Нужно определить реального пользователя процесса и необходимые права.

### Ошибка 5. Считать active (running) доказательством работоспособности

Приложение может работать как процесс, но возвращать HTTP 500 или не иметь доступа к базе данных.

### Ошибка 6. Исправлять только последствия

Например, изменение владельца файла журнала может временно восстановить сервис.

Но если неправильный владелец назначается через logrotate, проблема возникнет снова.

Поэтому важно устранять root cause.

## 15. Главный принцип диагностики

При возникновении неисправности:

1. Определить симптомы.
2. Проверить состояние сервиса.
3. Изучить журнал.
4. Проверить конфигурацию и зависимости.
5. Сформулировать гипотезу.
6. Подтвердить root cause.
7. Внести минимальное исправление.
8. Проверить работу приложения.
9. Убедиться, что проблема не повторится.

Главный принцип Linux Administrator / DevOps:

> Сначала диагностика → затем подтверждение причины → минимальное исправление → проверка результата.
