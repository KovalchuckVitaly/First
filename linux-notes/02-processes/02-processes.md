# Module 02 — Linux Processes

## 1. Что такое процесс

**Процесс (process)** — это запущенный экземпляр программы.

У каждого процесса есть различные характеристики:

- `PID` — Process ID, уникальный идентификатор процесса;
- `PPID` — Parent Process ID, PID родительского процесса;
- состояние (`R`, `S`, `D`, `T`, `Z`);
- пользователь, от имени которого работает процесс;
- приоритет;
- открытые файловые дескрипторы;
- используемые ресурсы.

Посмотреть информацию о конкретном процессе:

```bash
# Показывает PID, PPID, пользователя, состояние и команду процесса.
ps -p 1234 -o pid,ppid,user,stat,cmd
```

---

## 2. Parent и Child процессы

Процессы в Linux образуют иерархию.

Когда Bash запускает внешнюю программу, упрощённо происходит следующее:

```text
Bash
  |
  | fork()
  v
Child process
  |
  | execve()
  v
Program
```

`fork()` создаёт новый дочерний процесс.

`execve()` заменяет выполняемую программу дочернего процесса на другую программу.

Например:

```bash
# Bash запускает программу sleep с аргументом 300.
sleep 300
```

В этом случае:

```text
Bash
 │
 │ parent
 ▼
sleep
```

`sleep` получает собственный `PID`, а PID Bash будет его `PPID`.

## 3. Состояния процессов

Основные состояния:

| Состояние | Значение |
|---|---|
| `R` | Running / Runnable |
| `S` | Interruptible Sleep |
| `D` | Uninterruptible Sleep |
| `T` | Stopped |
| `Z` | Zombie |

### R — Running / Runnable

Процесс:

- либо прямо сейчас выполняется на CPU;
- либо готов выполняться и ожидает получения CPU.

Важно:

`R` не означает, что процесс обязательно прямо сейчас физически выполняется на процессоре.

Например, если одно ядро и десять процессов находятся в `R`, физически ядро может выполнять только один из них в конкретный момент времени.

---

### S — Interruptible Sleep

Процесс чего-то ожидает:

- таймер;
- данные;
- событие;
- ввод;
- другой ресурс.

Например:

```bash
# Процесс большую часть времени будет находиться в S,
# ожидая окончания 300-секундного таймера.
sleep 300
```

Такой процесс обычно практически не использует CPU во время ожидания.

---

### D — Uninterruptible Sleep

Процесс находится в непрерываемом ожидании операции внутри ядра.

Часто это связано с I/O:

- диск;
- filesystem;
- NFS;
- network storage;
- другое устройство.

Пока процесс остаётся в `D`, даже `SIGKILL` не сможет завершить его **немедленно**.

Поэтому:

```bash
# SIGKILL не является универсальным решением процесса,
# который долго находится в D.
kill -9 PID
```

Если процесс долго находится в `D`, нужно искать причину ожидания.

Например:

```bash
# Показывает последние сообщения ядра.
# Можно искать I/O errors, filesystem errors и другие проблемы.
dmesg | tail -n 100
```

---

### T — Stopped

Выполнение процесса остановлено.

Например:

```text
Ctrl+Z
   ↓
SIGTSTP
   ↓
T
```

Также процесс можно остановить принудительно:

```bash
# Отправляет процессу SIGSTOP.
kill -SIGSTOP PID
```

Продолжить выполнение:

```bash
# Отправляет SIGCONT и разрешает процессу продолжить работу.
kill -SIGCONT PID
```

---

### Z — Zombie

Zombie — это **уже завершившийся процесс**, для которого родитель ещё не забрал информацию о завершении.

Жизненный цикл:

```text
Child работает
      ↓
Child завершается
      ↓
ядро сохраняет exit status
      ↓
Child становится Zombie (Z)
      ↓
Parent вызывает wait()/waitpid()
      ↓
Parent получает exit status
      ↓
ядро удаляет запись Zombie
```

### Важно

**Именно Parent вызывает `wait()` / `waitpid()`.**

Zombie сам ничего не вызывает и ничего не выполняет.

Поэтому:

```bash
# Бессмысленно для Zombie:
# процесс уже завершён.
kill -9 ZOMBIE_PID
```

Если множество Zombie имеют одинаковый `PPID`, необходимо расследовать их родительский процесс.

## 4. Orphan Process

**Orphan** — живой процесс, первоначальный родитель которого завершился.

Например:

```text
Parent
  │
  └── Child
```

Parent завершается:

```text
Parent → terminated

Child → продолжает работать
          ↓
        Orphan
          ↓
      Reparenting
          ↓
       New Parent
```

При этом `PPID` дочернего процесса изменится.

Очень важно не путать:

```text
Zombie
→ процесс УЖЕ завершён
→ родитель ещё не забрал exit status

Orphan
→ процесс ЖИВ
→ его первоначальный родитель завершился
```

Завершение родителя **не означает автоматически**, что Linux отправляет всем его детям `SIGHUP`.

## 5. Foreground и Background

### Foreground

Если выполнить:

```bash
# Запускает sleep как foreground job.
sleep 300
```

Bash ожидает завершения или остановки foreground job.

Пока `sleep` работает, обычный prompt Bash недоступен.

---

### Background

Добавление `&`:

```bash
# Запускает sleep как background job.
sleep 300 &
```

означает:

> Запустить команду в background и сразу вернуть управление Bash.

Например:

```text
[1] 5000
```

где:

```text
[1]  → Job ID
5000 → PID
```

**Job ID и PID — разные вещи.**

---

## 6. Bash Job Control

Посмотреть jobs текущего Bash:

```bash
# Показывает задания текущего shell.
jobs
```

Остановить foreground job:

```text
Ctrl+Z
```

Обычно:

```text
Ctrl+Z → SIGTSTP
```

Продолжить job №1 в background:

```bash
# Продолжает выполнение job №1 в фоне.
bg %1
```

Вернуть job №1 в foreground:

```bash
# Переводит job №1 на передний план терминала.
fg %1
```

При:

```text
Ctrl+Z → bg → fg
```

PID процесса не меняется.

---

## 7. SIGTSTP и SIGSTOP

Оба сигнала могут остановить процесс, но работают немного по-разному.

### SIGTSTP

Обычно связан с:

```text
Ctrl+Z
```

Процесс может установить обработчик этого сигнала или проигнорировать его.

---

### SIGSTOP

```bash
# Принудительно останавливает процесс.
kill -SIGSTOP PID
```

`SIGSTOP` нельзя:

- обработать;
- проигнорировать;
- заблокировать.

В этом смысле он похож на `SIGKILL`.

Продолжить остановленный процесс:

```bash
# Продолжает выполнение остановленного процесса.
kill -SIGCONT PID
```

---

## 8. Сигналы

**Signal** — механизм уведомления и управления процессами.

Посмотреть список сигналов:

```bash
# Показывает известные kill сигналы.
kill -l
```

Основные сигналы:

| Signal | Обычно № | Назначение |
|---|---:|---|
| `SIGHUP` | 1 | Hangup |
| `SIGINT` | 2 | Interrupt |
| `SIGKILL` | 9 | Принудительное завершение |
| `SIGTERM` | 15 | Запрос на завершение |
| `SIGCONT` | 18 | Продолжить процесс |
| `SIGSTOP` | 19 | Принудительно остановить |
| `SIGTSTP` | 20 | Terminal Stop |

Для некоторых сигналов номера могут различаться между архитектурами, поэтому использование имён обычно понятнее.

---

## 9. SIGTERM и SIGKILL

Обычная команда:

```bash
# По умолчанию отправляет SIGTERM.
kill PID
```

эквивалентна отправке:

```text
SIGTERM (15)
```

`SIGTERM` — запрос процессу на завершение.

Приложение получает возможность выполнить **graceful shutdown**, например:

```text
SIGTERM
   ↓
перестать принимать новые запросы
   ↓
завершить текущую работу
   ↓
сохранить необходимое состояние
   ↓
закрыть ресурсы
   ↓
завершиться
```

При этом программа может обработать или проигнорировать `SIGTERM`.

---

Принудительное завершение:

```bash
# Отправляет SIGKILL.
kill -9 PID
```

`SIGKILL` нельзя:

- обработать;
- проигнорировать;
- заблокировать.

Программа не получает возможности выполнить application-level cleanup.

Поэтому общее правило:

```text
Сначала SIGTERM
      ↓
проверить результат
      ↓
SIGKILL только при необходимости
```

---

## 10. kill, pkill и killall

### kill

Работа с конкретным PID:

```bash
# Отправляет SIGTERM процессу 1234.
kill 1234
```

Технически правильнее говорить:

> `kill` отправляет сигнал процессу.

Потому что сигнал не обязательно завершает процесс.

Например:

```bash
# Останавливает процесс, но не завершает его.
kill -SIGSTOP 1234
```

---

### pkill

Ищет процессы по имени/критериям и отправляет им сигнал.

```bash
# Находит подходящие процессы sleep
# и отправляет им SIGTERM.
pkill sleep
```

Удобная модель:

```text
pgrep
→ найти процессы

pkill
→ найти процессы + отправить сигнал
```

---

### killall

```bash
# Отправляет SIGTERM процессам с именем sleep.
killall sleep
```

Упрощённая модель:

```text
kill PID
→ конкретный PID

pkill criteria
→ поиск по критериям + сигнал

killall name
→ процессы с указанным именем
```

---

## 11. Поиск процессов

### ps

```bash
# Показывает процессы согласно стандартным условиям ps.
ps
```

Это **не обязательно все процессы системы**.

Все процессы:

```bash
# -e — все процессы.
# -f — расширенный формат.
ps -ef
```

Конкретный PID:

```bash
# Показывает PID, PPID, состояние и команду процесса.
ps -p 1234 -o pid,ppid,stat,cmd
```

---

### pgrep

```bash
# Ищет процессы nginx и выводит их PID.
pgrep nginx
```

---

### grep

Традиционный вариант:

```bash
# ps выводит процессы,
# grep фильтрует строки, содержащие nginx.
ps -ef | grep nginx
```

При этом в результате иногда появляется:

```text
grep nginx
```

потому что сам `grep` тоже является процессом.

---

### jobs

```bash
# Показывает jobs текущего Bash.
jobs
```

Важно:

```text
jobs ≠ все процессы системы
```

Процесс может существовать в системе и при этом отсутствовать в `jobs`.

## 12. Scheduler

Scheduler решает:

> Какой runnable-процесс должен получить CPU?

Если runnable-процессов больше, чем доступных CPU, они конкурируют за процессорное время.

Например:

```text
1 CPU
8 CPU-bound процессов
```

В конкретный момент физически выполняться на этом CPU может только одна задача, но Scheduler очень быстро переключает выполнение между runnable-процессами.

На нескольких CPU процессы могут выполняться параллельно.

Например:

```text
4 логических CPU
4 CPU-bound однопоточных процесса
```

Все четыре потенциально могут одновременно использовать примерно по одному CPU.

## 13. nice и renice

`nice` влияет на относительный CPU-приоритет обычного процесса.

Диапазон:

```text
-20 ........ 0 ........ 19
 ↑                       ↑
выше                    ниже
CPU priority            CPU priority
```

То есть:

```text
nice = -20 → высокий приоритет
nice = 0   → стандартный
nice = 19  → низкий приоритет
```

Запуск программы:

```bash
# Запускает программу с nice=10.
nice -n 10 command
```

Изменение уже существующего процесса:

```bash
# Устанавливает nice=15 процессу с указанным PID.
renice 15 -p PID
```

Обычный пользователь может сделать свой процесс менее приоритетным.

Но повышение CPU-приоритета требует соответствующих прав.

### Важно

`nice` — **не CPU limit**.

Например:

```text
Process A → nice=19
```

Если других CPU-bound runnable-процессов нет:

```text
Process A → может использовать ~100% одного CPU
```

Но если появляется конкурент:

```text
Process A → nice=19
Process B → nice=0
```

Process B будет получать значительно большую долю CPU.

---

## 14. nohup

`nohup` используется для запуска программы с игнорированием `SIGHUP`.

```bash
# nohup — игнорирование SIGHUP.
# & — запуск в background.
nohup ./backup.sh &
```

Важно разделять:

```text
nohup
→ SIGHUP

&
→ background
```

`nohup` также обрабатывает стандартные потоки, если они связаны с терминалом.

`nohup` **не является механизмом reparenting**.

---

## 15. disown

`disown` — механизм Bash Job Control.

Например:

```bash
# Запускаем процесс в background.
sleep 1000 &
```

Проверяем:

```bash
# Показываем jobs текущего Bash.
jobs
```

Убираем job №1 из таблицы jobs:

```bash
# Bash перестаёт управлять этим заданием как своим job.
disown %1
```

После этого:

```bash
jobs
```

может ничего не показать.

Но процесс продолжает существовать.

Проверить его можно:

```bash
# Проверяем процесс непосредственно по PID.
ps -p PID -o pid,ppid,stat,cmd
```

Удобная модель:

```text
&       → запустить в background

nohup   → защита от SIGHUP

disown  → убрать существующий job
          из Job Control текущего Bash
```

## 16. Базовая диагностика процесса

Если production-процесс не завершился после `SIGTERM`, не нужно автоматически выполнять:

```bash
kill -9 PID
```

Сначала нужно разобраться, что происходит.

### Проверить процесс

```bash
# Показывает родителя, состояние, CPU и команду процесса.
ps -p PID -o pid,ppid,stat,pcpu,cmd
```

### Проверить systemd-сервис

```bash
# Показывает текущее состояние сервиса.
systemctl status SERVICE
```

### Посмотреть журнал сервиса

```bash
# Показывает журнал конкретного systemd unit.
journalctl -u SERVICE
```

### Посмотреть сообщения ядра

```bash
# Последние сообщения kernel ring buffer.
dmesg | tail -n 100
```

Для CentOS 7:

```bash
# Просмотр последних сообщений основного системного лога.
tail -n 100 /var/log/messages
```

Общая логика:

```text
Процесс ведёт себя неправильно
          ↓
Проверить состояние
          ↓
Проверить приложение/сервис
          ↓
Проверить логи
          ↓
При необходимости проверить kernel/I/O
          ↓
Понять последствия остановки
          ↓
SIGKILL только если действительно необходимо
```

# Краткая шпаргалка

```text
PID  → ID процесса
PPID → ID родителя

R → Running / Runnable
S → Interruptible Sleep
D → Uninterruptible Sleep
T → Stopped
Z → Zombie
```

```text
Zombie
→ уже завершён
→ Parent должен вызвать wait()/waitpid()

Orphan
→ ещё жив
→ первоначальный Parent завершился
→ происходит reparenting
```

```text
Ctrl+Z → SIGTSTP

SIGSTOP → принудительная остановка
SIGCONT → продолжение

SIGTERM → запрос на завершение
SIGKILL → принудительное завершение
```

```text
jobs  → jobs текущего Bash
ps    → информация о процессах
pgrep → поиск процессов
```

```text
&       → background
nohup   → игнорирование SIGHUP
disown  → убрать job из Job Control Bash
```

```text
nice -20 → высокий CPU priority
nice 0   → обычный
nice 19  → низкий CPU priority

nice ≠ CPU limit
```

## Три вещи, которые нельзя путать

### 1. wait()

**Parent вызывает `wait()` / `waitpid()` и получает exit status завершившегося Child.**

### 2. Ctrl+Z

```text
Ctrl+Z → SIGTSTP
```

Не `SIGSTOP`.

### 3. Смерть Parent и SIGHUP

```text
Parent завершился
→ живой Child может стать Orphan
→ reparenting
```

Это **не означает автоматически**:

```text
Parent завершился
→ SIGHUP всем Child
```
