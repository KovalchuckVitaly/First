# Module 02 — Linux Processes

## 1. Что такое процесс

**Процесс (process)** — это запущенный экземпляр программы.

Программа — это исполняемый код, хранящийся на диске. Процесс появляется, когда этот код запускается и начинает выполняться операционной системой.

У процесса есть различные характеристики:

- `PID` — Process ID;
- `PPID` — Parent Process ID;
- состояние;
- пользователь, от имени которого он выполняется;
- приоритет;
- открытые файловые дескрипторы;
- используемые ресурсы.

Посмотреть информацию о конкретном процессе:

```bash
# Показывает PID, PPID, пользователя, состояние и команду процесса.
ps -p 1234 -o pid,ppid,user,stat,cmd
```

---

## 2. PID и PPID

### PID

**PID (Process ID)** — уникальный идентификатор процесса в системе на момент его существования.

Например:

```text
PID
5000    bash
5100    sleep
```

PID используется многими административными командами.

Например:

```bash
# Отправляет сигнал SIGTERM процессу с PID 5100.
kill 5100
```

### PPID

**PPID (Parent Process ID)** — PID родительского процесса.

Например:

```text
PID    PPID    COMMAND
5000   1000    bash
5100   5000    sleep
```

Здесь:

```text
bash PID = 5000

sleep PID  = 5100
sleep PPID = 5000
```

Следовательно, `bash` является родителем `sleep`.

---

## 3. Parent и Child процессы

Процессы Linux образуют иерархию.

Процесс может создавать дочерние процессы.

Упрощённо запуск внешней программы из Bash можно представить так:

```text
Bash
  |
  | fork()
  v
Child process
  |
  | execve()
  v
Program
```

### fork()

`fork()` создаёт новый дочерний процесс на основе существующего процесса.

### execve()

`execve()` заменяет выполняемую программу процесса новой программой.

Например:

```bash
# Bash запускает программу sleep с аргументом 300.
sleep 300
```

Упрощённо:

```text
Bash
  |
  | fork()
  v
Child
  |
  | execve()
  v
sleep 300
```

В результате `sleep` получает собственный PID, а PID Bash становится его PPID.

# 4. Состояния процессов

Основные состояния процессов:

| State | Название | Значение |
|---|---|---|
| `R` | Running / Runnable | выполняется или готов выполняться |
| `S` | Interruptible Sleep | прерываемое ожидание |
| `D` | Uninterruptible Sleep | непрерываемое ожидание |
| `T` | Stopped | остановлен |
| `Z` | Zombie | завершён, но не обработан родителем |

---

## 4.1 R — Running / Runnable

Состояние `R` означает, что процесс:

- прямо сейчас выполняется на CPU;

или

- готов выполняться и ожидает получения CPU.

Поэтому `R` не означает, что процесс обязательно физически выполняется на процессоре именно в данный момент.

Например:

```text
1 CPU
8 процессов в состоянии R
```

В конкретный момент один CPU может выполнять только одну задачу, поэтому остальные runnable-задачи ожидают получения процессорного времени.

---

## 4.2 S — Interruptible Sleep

`S` означает **Interruptible Sleep**.

Процесс чего-то ожидает:

- окончания таймера;
- данных;
- события;
- ввода;
- освобождения ресурса.

Например:

```bash
# sleep большую часть времени находится в состоянии S,
# ожидая окончания таймера.
sleep 300
```

Пока процесс ожидает событие, CPU для выполнения его кода ему обычно не нужен.

Ожидание называется **interruptible**, потому что оно может быть прервано соответствующим сигналом.

---

## 4.3 D — Uninterruptible Sleep

`D` означает **Uninterruptible Sleep**.

Процесс ожидает завершения операции внутри ядра. Часто такое состояние связано с I/O:

- диском;
- filesystem;
- NFS;
- network storage;
- другим устройством.

Важно:

Пока процесс остаётся в `D`, даже `SIGKILL` не сможет завершить его немедленно.

Сигнал может ожидать обработки до тех пор, пока процесс не выйдет из непрерываемого ожидания.

Поэтому длительное состояние `D` требует расследования причины, а не многократного выполнения:

```bash
# Не является универсальным решением процесса в состоянии D.
kill -9 PID
```

---

## 4.4 T — Stopped

`T` означает, что выполнение процесса остановлено.

Например, foreground-процесс можно остановить сочетанием:

```text
Ctrl+Z
```

Обычно это приводит к:

```text
Ctrl+Z
   ↓
SIGTSTP
   ↓
T
```

Процесс остаётся существовать, но его выполнение остановлено.

Продолжить выполнение можно с помощью `SIGCONT`.

---

## 4.5 Z — Zombie

**Zombie** — уже завершившийся процесс, для которого родитель ещё не забрал информацию о завершении.

Жизненный цикл:

```text
Child работает
      ↓
Child завершается
      ↓
ядро сохраняет exit status
      ↓
Child становится Zombie
      ↓
Parent вызывает wait()/waitpid()
      ↓
Parent получает exit status
      ↓
ядро удаляет запись Zombie
```

### Важно

**Именно Parent вызывает `wait()` / `waitpid()`.**

Zombie сам ничего не вызывает.

Zombie уже не выполняет код, поэтому:

```bash
# Не поможет удалить Zombie.
kill -9 ZOMBIE_PID
```

`SIGKILL` не может завершить процесс, который уже завершён.

Если в системе появляется большое количество Zombie с одинаковым `PPID`, необходимо расследовать родительский процесс и выяснить, почему он не забирает статусы завершившихся детей.

---

# 5. Orphan Process

**Orphan** — живой процесс, первоначальный родитель которого завершился.

Например:

```text
Parent
  |
  └── Child
```

Если Parent завершился, а Child продолжает работать:

```text
Parent terminates
       ↓
Child продолжает работать
       ↓
Orphan
       ↓
Reparenting
       ↓
New Parent
```

У процесса появляется новый родитель, поэтому его `PPID` изменяется.

Важно различать Zombie и Orphan:

```text
Zombie
→ процесс УЖЕ завершён
→ Parent ещё не забрал exit status

Orphan
→ процесс ЖИВ
→ его первоначальный Parent завершился
```

Завершение родителя само по себе **не означает**, что Linux автоматически отправит всем его дочерним процессам `SIGHUP`.

# 6. Foreground и Background

Процессы, связанные с терминалом, могут работать в foreground или background.

## Foreground

Например:

```bash
# Запускает sleep как foreground job.
sleep 300
```

Bash ждёт завершения или остановки foreground job.

Пока foreground job выполняется, обычный prompt Bash недоступен.

Foreground process group также имеет особое отношение к управляющему терминалу: именно она обычно получает терминально-сгенерированные сигналы и имеет право читать ввод из терминала.

---

## Background

Добавление `&`:

```bash
# Запускает sleep как background job.
sleep 300 &
```

означает:

> Запустить команду в background и сразу вернуть управление Bash.

Например:

```text
[1] 5000
```

где:

```text
[1]  → Job ID
5000 → PID
```

`Job ID` и `PID` — разные идентификаторы.

---

# 7. Bash Job Control

Bash имеет собственный механизм управления заданиями — **Job Control**.

Посмотреть задания текущего Bash:

```bash
# Показывает jobs текущего shell.
jobs
```

Важно:

```text
jobs ≠ все процессы системы
```

`jobs` показывает задания, которыми управляет именно текущий shell.

Процесс может существовать в Linux, но отсутствовать в выводе `jobs`.

---

## Ctrl+Z

Foreground job можно остановить:

```text
Ctrl+Z
```

Обычно терминал инициирует отправку:

```text
SIGTSTP
```

После этого процесс остаётся существовать, но его выполнение останавливается.

---

## bg

```bash
# Продолжает выполнение job №1 в background.
bg %1
```

Если job был остановлен, Bash продолжает его выполнение, используя механизм `SIGCONT`.

---

## fg

```bash
# Переводит job №1 в foreground текущего терминала.
fg %1
```

Если job был остановлен, его выполнение продолжается.

`fg` не просто отправляет `SIGCONT`: Bash также делает соответствующую process group foreground-группой терминала.

При:

```text
Ctrl+Z → bg → fg
```

новый процесс не создаётся, поэтому PID не меняется.

---

# 8. Background и ввод из терминала

Background-процесс обычно не должен читать ввод из управляющего терминала.

Например:

```bash
# Запускает cat в background.
cat &
```

`cat` без аргументов пытается читать `stdin`.

Если `stdin` связан с управляющим терминалом:

```text
cat работает в background
        ↓
пытается читать terminal
        ↓
SIGTTIN
        ↓
Stopped
```

Это предотвращает конфликт между foreground и background jobs за ввод терминала.

Если `stdin` поступает из файла:

```bash
# stdin поступает из /etc/hosts,
# поэтому cat не требуется читать терминал.
cat < /etc/hosts &
```

процесс может нормально выполниться в background.

# 9. Сигналы

**Signal** — механизм уведомления и управления процессами.

Посмотреть доступные сигналы:

```bash
# Выводит список сигналов.
kill -l
```

Основные сигналы:

| Signal | Обычно № | Назначение |
|---|---:|---|
| `SIGHUP` | 1 | Hangup |
| `SIGINT` | 2 | Interrupt |
| `SIGKILL` | 9 | принудительное завершение |
| `SIGTERM` | 15 | запрос на завершение |
| `SIGCONT` | 18 | продолжить остановленный процесс |
| `SIGSTOP` | 19 | принудительно остановить |
| `SIGTSTP` | 20 | Terminal Stop |

Номера некоторых сигналов могут различаться между архитектурами, поэтому имена сигналов обычно понятнее и безопаснее для чтения команд.

---

# 10. SIGTERM и SIGKILL

## SIGTERM

Команда:

```bash
# По умолчанию kill отправляет SIGTERM.
kill PID
```

по умолчанию отправляет `SIGTERM`.

Это запрос процессу на завершение.

Приложение может обработать этот сигнал и выполнить **graceful shutdown**:

```text
SIGTERM
   ↓
перестать принимать новые задачи
   ↓
закончить текущие операции
   ↓
сохранить необходимое состояние
   ↓
закрыть ресурсы
   ↓
завершиться
```

Программа также может обработать `SIGTERM` иначе или проигнорировать его.

Поэтому `SIGTERM` даёт **возможность** корректно завершиться, но не гарантирует это.

---

## SIGKILL

```bash
# Отправляет SIGKILL.
kill -9 PID
```

`SIGKILL` нельзя:

- обработать;
- проигнорировать;
- заблокировать.

Процесс не получает возможности выполнить application-level cleanup.

Поэтому стандартная логика:

```text
SIGTERM
   ↓
проверить результат
   ↓
SIGKILL только при необходимости
```

---

# 11. SIGTSTP и SIGSTOP

Оба сигнала могут остановить выполнение процесса, но между ними есть важное различие.

## SIGTSTP

Обычно связан с:

```text
Ctrl+Z
```

Процесс может установить обработчик `SIGTSTP` или проигнорировать его.

## SIGSTOP

```bash
# Принудительно останавливает процесс.
kill -SIGSTOP PID
```

`SIGSTOP` нельзя:

- обработать;
- проигнорировать;
- заблокировать.

В этом отношении он похож на `SIGKILL`.

Продолжить остановленный процесс:

```bash
# Разрешает остановленному процессу продолжить выполнение.
kill -SIGCONT PID
```

# 12. kill, pkill и killall

## kill

`kill` отправляет сигнал процессу по PID.

```bash
# Отправляет SIGTERM процессу 1234.
kill 1234
```

Технически правильнее говорить:

> `kill` отправляет сигнал.

Потому что сигнал не обязательно завершает процесс.

Например:

```bash
# Останавливает процесс, а не завершает его.
kill -SIGSTOP 1234
```

---

## pkill

`pkill` ищет процессы по имени или другим критериям и отправляет им сигнал.

```bash
# Находит подходящие процессы sleep
# и отправляет им SIGTERM.
pkill sleep
```

Удобная модель:

```text
pgrep
→ найти процессы

pkill
→ найти процессы + отправить сигнал
```

---

## killall

```bash
# Отправляет SIGTERM процессам с именем sleep.
killall sleep
```

Упрощённо:

```text
kill PID
→ известен конкретный PID

pkill criteria
→ поиск процессов по критериям + сигнал

killall name
→ воздействие на процессы с указанным именем
```

# 13. Просмотр и поиск процессов

## ps

```bash
# Показывает процессы согласно стандартным правилам отбора ps.
ps
```

Обычный `ps` не означает «показать все процессы системы».

Например:

```bash
# -e — выбирает все процессы.
# -f — расширенный формат вывода.
ps -ef
```

Конкретный процесс:

```bash
# Показывает PID, PPID, состояние и команду.
ps -p 1234 -o pid,ppid,stat,cmd
```

---

## pgrep

```bash
# Ищет процессы nginx и выводит их PID.
pgrep nginx
```

---

## ps + grep

Также часто используется:

```bash
# ps выводит процессы,
# grep оставляет строки, содержащие nginx.
ps -ef | grep nginx
```

При этом среди результатов может появиться:

```text
grep nginx
```

потому что `grep` сам является процессом.

# 14. Scheduler

**Scheduler** решает, какие runnable-задачи должны получить CPU.

Если runnable-задач больше, чем доступных CPU, они конкурируют за процессорное время.

Например:

```text
1 CPU
8 CPU-bound процессов
```

В конкретный момент один CPU выполняет одну задачу, а Scheduler распределяет процессорное время между runnable-задачами.

Если системе доступны несколько CPU, несколько задач могут выполняться физически параллельно.

Например:

```text
4 CPU
4 CPU-bound однопоточных процесса
```

Каждый процесс потенциально может использовать примерно один CPU.

# 15. nice и renice

`nice` влияет на относительный CPU-приоритет обычных процессов.

Диапазон nice:

```text
-20 ........ 0 ........ 19
 ↑                       ↑
выше                    ниже
CPU priority            CPU priority
```

То есть:

```text
nice = -20 → высокий CPU priority
nice = 0   → стандартный
nice = 19  → низкий CPU priority
```

Запустить программу с определённым nice:

```bash
# Запускает command с nice=10.
nice -n 10 command
```

Изменить nice существующего процесса:

```bash
# Устанавливает nice=15 существующему процессу.
renice 15 -p PID
```

Обычный пользователь может сделать свой процесс менее приоритетным, увеличивая nice.

Повышение CPU-приоритета требует соответствующих привилегий.

### nice не является CPU limit

Например:

```text
Process A
nice = 19
```

Если других конкурирующих CPU-bound процессов нет:

```text
Process A
→ может использовать практически 100% одного CPU
```

При появлении конкурента:

```text
Process A → nice=19
Process B → nice=0
```

Process B будет получать значительно большую долю процессорного времени.

# 16. nohup

`nohup` запускает программу с игнорированием `SIGHUP`.

```bash
# nohup — запуск с игнорированием SIGHUP.
# & — запуск в background.
nohup ./backup.sh &
```

Необходимо разделять:

```text
nohup
→ работа с SIGHUP

&
→ background
```

`nohup` также может перенаправлять стандартные потоки, если они связаны с терминалом.

Важно:

`nohup` не является механизмом reparenting.

Если родитель завершился и живой процесс получает нового родителя — это отдельный механизм Linux.

---

# 17. disown

`disown` относится к Bash Job Control.

Например:

```bash
# Запускает процесс как background job.
sleep 1000 &
```

Посмотреть jobs:

```bash
# Показывает jobs текущего Bash.
jobs
```

Удалить job №1 из таблицы jobs Bash:

```bash
# Bash перестаёт управлять job №1 как своим заданием.
disown %1
```

После этого процесс не обязан завершаться.

Он может продолжать существовать в системе, хотя:

```bash
jobs
```

его больше не показывает.

Проверить существование процесса можно через `ps`.

Удобная модель:

```text
&       → запустить в background

nohup   → запустить с игнорированием SIGHUP

disown  → убрать существующий job
          из Job Control текущего Bash
```
