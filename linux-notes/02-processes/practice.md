# Module 02 — Linux Processes: Practice

В этом файле собраны практические эксперименты с процессами, выполненные во время изучения модуля.

Среда:

```text
OS: CentOS Linux 7
Shell: Bash
```

# 1. Запуск процесса в foreground

Запускаем:

```bash
# Запускает sleep на 300 секунд в foreground.
sleep 300
```

Пока `sleep` работает, Bash ожидает его завершения и не возвращает prompt.

В другом терминале процесс можно найти:

```bash
# Ищет процессы с именем sleep и выводит их PID.
pgrep sleep
```

Посмотреть состояние:

```bash
# Показывает PID, PPID, состояние и команду процесса.
ps -p PID -o pid,ppid,stat,cmd
```

Для `sleep` ожидаем состояние:

```text
S
```

поскольку процесс ожидает окончания таймера и CPU в это время ему практически не требуется.

---

# 2. Запуск процесса в background

```bash
# & запускает sleep как background job.
sleep 300 &
```

Bash сразу возвращает prompt.

Пример:

```text
[1] 5000
```

где:

```text
[1]  → Job ID
5000 → PID
```

Проверяем:

```bash
# Показывает jobs текущего Bash.
jobs
```

---

# 3. Ctrl+Z, bg и fg

Запускаем:

```bash
# Запускает sleep в foreground.
sleep 300
```

Нажимаем:

```text
Ctrl+Z
```

Процесс получает `SIGTSTP` и останавливается.

Проверяем:

```bash
# Показывает состояние jobs текущего Bash.
jobs
```

Пример:

```text
[1]+  Stopped    sleep 300
```

Продолжаем выполнение в background:

```bash
# Продолжает job №1 в background.
bg %1
```

Возвращаем в foreground:

```bash
# Переводит job №1 обратно в foreground.
fg %1
```

### Вывод

```text
Ctrl+Z
   ↓
SIGTSTP
   ↓
Stopped (T)
   ↓
bg
   ↓
SIGCONT + background
   ↓
fg
   ↓
foreground
```

PID процесса при этих операциях не меняется.

# 4. SIGSTOP и SIGCONT

Запускаем:

```bash
# Запускает процесс в background.
sleep 300 &
```

Получаем его PID:

```bash
# Ищет PID процесса sleep.
pgrep sleep
```

Принудительно останавливаем:

```bash
# Отправляет SIGSTOP процессу.
kill -SIGSTOP PID
```

Проверяем:

```bash
# Показывает состояние процесса.
ps -p PID -o pid,stat,cmd
```

Процесс должен находиться в состоянии `T`.

Продолжаем:

```bash
# Отправляет SIGCONT остановленному процессу.
kill -SIGCONT PID
```

### Вывод

`SIGSTOP` останавливает процесс принудительно.

`SIGCONT` разрешает остановленному процессу продолжить выполнение.

# 5. Background-процесс и ввод из терминала

Запускаем:

```bash
# Запускает cat в background.
cat &
```

`cat` пытается читать `stdin` из терминала, несмотря на то что находится в background.

Проверяем:

```bash
# Показывает jobs текущего Bash.
jobs
```

Получаем состояние вида:

```text
Stopped
```

Причина:

```text
cat находится в background
        ↓
пытается читать terminal
        ↓
SIGTTIN
        ↓
Stopped
```

Возвращаем `cat` в foreground:

```bash
# Делает cat foreground job.
fg %1
```

Теперь процесс может нормально читать ввод с терминала.

### Вывод

Background job не должен конкурировать с foreground job за чтение из управляющего терминала.

# 6. Background cat с перенаправлением stdin

Проверяем, что проблема предыдущего эксперимента связана именно с terminal input:

```bash
# cat работает в background,
# но stdin получает из файла /etc/hosts.
cat < /etc/hosts &
```

Теперь `cat` не требуется читать клавиатуру.

Он читает файл, выводит содержимое и завершается.

Можно перенаправить также stdout:

```bash
# stdin читается из /etc/hosts,
# stdout записывается в output.txt,
# процесс работает в background.
cat < /etc/hosts > output.txt &
```

Проверяем:

```bash
# Показывает содержимое созданного файла.
cat output.txt
```

### Вывод

```text
stdin  → /etc/hosts
stdout → output.txt
```

Процессу не требуется использовать terminal через stdin/stdout.

# 7. SIGTERM

Запускаем:

```bash
# Запускает sleep в background.
sleep 300 &
```

Находим PID:

```bash
# Ищет PID процесса sleep.
pgrep sleep
```

Отправляем:

```bash
# По умолчанию kill отправляет SIGTERM.
kill PID
```

Проверяем:

```bash
# Проверяем, существует ли процесс.
ps -p PID -o pid,stat,cmd
```

`sleep` должен завершиться.

### Вывод

Обычный:

```bash
kill PID
```

отправляет:

```text
SIGTERM (15)
```

# 8. Zombie Process

Во время изучения процессов была рассмотрена ситуация, когда Child завершается, а Parent не вызывает `wait()` / `waitpid()`.

Результат:

```text
Child завершился
      ↓
ядро сохраняет exit status
      ↓
Zombie
```

Zombie можно обнаружить:

```bash
# Показывает все процессы с PID, PPID, состоянием и командой.
ps -e -o pid,ppid,stat,cmd
```

Для Zombie:

```text
STAT = Z
```

Попытка:

```bash
# Не поможет удалить Zombie,
# потому что процесс уже завершён.
kill -9 ZOMBIE_PID
```

не решает проблему.

Чтобы найти родителя:

```bash
# Показывает PID и PPID конкретного Zombie.
ps -p ZOMBIE_PID -o pid,ppid,stat,cmd
```

### Вывод

Решать необходимо проблему с Parent, который не забирает exit status завершившегося Child.

# 9. CPU-bound процесс с yes

Для проверки Scheduler использовалась команда:

```bash
# yes постоянно генерирует строки.
# stdout перенаправлен в /dev/null,
# чтобы терминал не заполнялся выводом.
yes > /dev/null &
```

`yes` практически постоянно готов выполнять вычисления и поэтому создаёт высокую нагрузку на CPU.

Находим процесс:

```bash
# Ищет PID процессов yes.
pgrep yes
```

Наблюдаем нагрузку:

```bash
# Интерактивно показывает процессы и использование ресурсов.
top
```

---

# 10. nice и конкуренция за один CPU

Были запущены несколько CPU-bound процессов `yes` с разными значениями nice.

Пример наблюдения:

```text
PID    PR    NI    S    %CPU    COMMAND
9392   20     0    R    83.1    yes
9244   30    10    R     8.6    yes
```

Процесс с:

```text
nice = 0
```

получал значительно больше процессорного времени, чем:

```text
nice = 10
```

При `nice=19` наблюдалось использование CPU примерно на уровне:

```text
1–2%
```

при наличии конкурирующих процессов с более высоким CPU priority.

### Важно

Эти значения **не являются фиксированными лимитами**.

Они являются результатом конкретного эксперимента и текущей конкуренции за CPU.

---

# 11. Процесс nice=19 без конкурентов

Отдельно проверялась гипотеза:

> Может ли процесс с `nice=19` использовать почти весь CPU?

Ответ:

```text
Да.
```

Если процесс является CPU-bound и ему не с кем конкурировать за CPU:

```text
nice = 19
      ↓
нет конкурентов
      ↓
может использовать ~100% одного CPU
```

### Вывод

`nice` задаёт относительный приоритет при конкуренции.

`nice` **не устанавливает CPU limit**.

# 12. Проверка нескольких CPU

В системе с четырьмя доступными CPU были запущены четыре CPU-bound процесса.

Наблюдение:

```text
4 CPU
+
4 CPU-bound процесса
        ↓
каждый процесс может использовать
примерно один CPU
```

В `top` каждый из процессов мог показывать около:

```text
97–98% CPU
```

Затем были добавлены CPU-bound процессы с `nice=19`.

При наличии четырёх процессов `nice=0`, занимающих доступные CPU, процессы `nice=19` получали лишь небольшую долю процессорного времени.

### Вывод

Scheduler учитывает `nice` именно при **конкуренции за CPU**.

# 13. renice

Изменить nice существующего процесса:

```bash
# Устанавливает процессу значение nice=19.
renice 19 -p PID
```

Обычный пользователь может сделать собственный процесс менее приоритетным.

Попытка повысить CPU priority обратно может закончиться:

```text
Permission denied
```

поскольку обычному пользователю нельзя произвольно повышать приоритет своих процессов.

### Вывод

```text
увеличить nice
→ уменьшить CPU priority
→ обычному пользователю разрешено

уменьшить nice
→ увеличить CPU priority
→ нужны соответствующие привилегии
```

# 14. nohup

Запускаем:

```bash
# nohup запускает sleep с игнорированием SIGHUP.
# & запускает процесс в background.
nohup sleep 300 &
```

Проверяем:

```bash
# Ищет PID sleep.
pgrep sleep
```

После завершения первоначального shell живой процесс может продолжить выполнение.

Если первоначальный Parent завершился, процесс будет reparented и его `PPID` изменится.

### Важно

Изменение PPID происходит **не из-за nohup**.

Это следствие завершения первоначального Parent и reparenting.

# 15. disown

Запускаем:

```bash
# Создаёт background job.
sleep 1000 &
```

Проверяем:

```bash
# sleep находится в таблице jobs текущего Bash.
jobs
```

Например:

```text
[1]+ Running    sleep 1000 &
```

Удаляем job:

```bash
# Убирает job №1 из Job Control текущего Bash.
disown %1
```

Снова:

```bash
# Проверяем jobs текущего Bash.
jobs
```

Процесса там уже нет.

Но это не означает, что он завершился.

Проверяем по PID:

```bash
# Проверяет существование процесса непосредственно через ps.
ps -p PID -o pid,ppid,stat,cmd
```

### Вывод

```text
jobs
→ состояние Job Control текущего Bash

ps
→ состояние процессов Linux
```

Удаление из `jobs` не означает завершение процесса.
