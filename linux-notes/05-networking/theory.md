# Module 05 — Linux Networking
## Theory

**Цель:** освоить сетевой минимум, нужный Junior DevOps для настройки Linux и диагностики типичных проблем подключения.

---

## 1. IP, MAC и порт: разные уровни

| Понятие | Уровень OSI | Назначение |
|---|---|---|
| MAC (Media Access Control) | Канальный, L2 | Доставка Ethernet-кадров между соседними узлами локального сегмента |
| IP (Internet Protocol) | Сетевой, L3 | Адресация узлов и маршрутизация пакетов между сетями |
| TCP/UDP-порт | Транспортный, L4 | Определение сетевого сокета и службы на узле |

Пример подключения клиента `192.168.10.25` к API `192.168.20.50:8080`:

- `192.168.10.25` — IP источника (клиента).
- `192.168.20.50` — IP назначения (сервера).
- `8080` — порт назначения.
- MAC-адреса используются для доставки кадров на каждом локальном участке маршрута. При переходе через маршрутизатор MAC-адреса в Ethernet-заголовках меняются.

На одном Linux-сервере может быть несколько IP-адресов и несколько интерфейсов.

## 2. LAN, switch, router, ARP

- **LAN (Local Area Network)** — локальная сеть.
- **Switch** обычно работает на L2: пересылает кадры по MAC-адресам.
- **Router** работает на L3: выбирает маршруты между IP-подсетями.
- **ARP (Address Resolution Protocol)** в IPv4 узнаёт MAC-адрес следующего узла по его IP в локальном канальном сегменте.

Если `10.0.0.50/24` обращается к `10.0.0.100`, то получатель находится в той же подсети и его MAC обычно определяется через ARP. Для удалённой подсети узел отправляет Ethernet-кадр на MAC своего следующего шлюза, сохраняя в IP-заголовке адрес конечного получателя.

```bash
ip neigh show
# Показывает соседей Linux (ARP для IPv4) и состояние записей.
```

Основные состояния соседей:

| Состояние | Значение |
|---|---|
| `REACHABLE` | Сосед недавно подтверждён как достижимый |
| `STALE` | Запись имеется, но её актуальность требуется подтвердить |
| `DELAY` | Перед активной проверкой соседа система ожидает некоторое время |
| `FAILED` | Разрешение адреса / проверка достижимости соседа не удалась |

`FAILED` указывает на проблему, но не доказывает одну конкретную причину.

## 3. Сетевые интерфейсы

```bash
ip -br addr
# Кратко показывает сетевые интерфейсы и назначенные IP-адреса.

ip -br link
# Кратко показывает состояние сетевых интерфейсов (канальный уровень).

ip addr show
# Показывает подробную информацию об IP-адресах интерфейсов.
```

Пример вывода:

```text
lo      UNKNOWN  127.0.0.1/8
ens33   UP       192.168.20.50/24
ens34   UP       10.0.0.50/24
```

`lo` — loopback-интерфейс. `127.0.0.1` обозначает сам узел: удалённый клиент не может подключиться к вашему серверу, обращаясь к `127.0.0.1` **на своей машине**.

## 4. CIDR и IPv4-подсети

**CIDR (Classless Inter-Domain Routing)** задаёт длину префикса сети. Например, `/24` означает 24 сетевых бита, а маска равна `255.255.255.0`.

| Префикс | Маска | Всего IPv4-адресов | Обычно адресов для устройств |
|---|---|---:|---:|
| `/24` | `255.255.255.0` | 256 | 254 |
| `/25` | `255.255.255.128` | 128 | 126 |
| `/26` | `255.255.255.192` | 64 | 62 |
| `/27` | `255.255.255.224` | 32 | 30 |
| `/28` | `255.255.255.240` | 16 | 14 |

Пример: сервер `192.168.10.70/27`.

- Адрес сети: `192.168.10.64`.
- Диапазон назначаемых адресов: `192.168.10.65–192.168.10.94`.
- Broadcast: `192.168.10.95`.
- Шаг таких подсетей — 32 адреса.

В таблице приведены обычные IPv4-подсети с выделенными network и broadcast адресами; для специальных случаев могут действовать другие правила.

## 5. Маршрутизация и Default Gateway

**Default Gateway** — маршрутизатор, через который отправляется пакет, если нет более конкретного подходящего маршрута.

```bash
ip route show
# Показывает текущую таблицу IP-маршрутизации.

ip route get 8.8.8.8
# Показывает маршрут, который ядро выберет для пакета к 8.8.8.8.

ip route get 192.168.10.25 from 192.168.20.50
# Проверяет маршрут до клиента с явно указанным исходным адресом.
```

Пример:

```text
default via 192.168.20.1 dev ens33
192.168.20.0/24 dev ens33 proto kernel scope link src 192.168.20.50
10.0.0.0/24 dev ens34 proto kernel scope link src 10.0.0.50
```

- `default` — маршрут по умолчанию.
- `via` — следующий шлюз.
- `dev` — интерфейс отправки пакета.
- `src` — предпочтительный исходный IP для нового локально создаваемого трафика.

Linux выбирает **наиболее конкретный подходящий маршрут** (*Longest Prefix Match*). Для непосредственно подключённой подсети отдельный IP-шлюз обычно не нужен.

**Асимметричная маршрутизация** — запрос поступает одним путём, ответ уходит другим. Это не обязательно неисправность. Чтобы доказать сетевую проблему, нужно подтвердить фактическую потерю или блокировку пакетов.

## 6. DNS — преобразование имён в IP

**DNS (Domain Name System)** позволяет получить IP-адрес по доменному имени, например `api.example.com`.

```bash
cat /etc/resolv.conf
# Показывает настройки системного DNS-резолвера; файл может управляться автоматически.

getent hosts api.example.com
# Проверяет разрешение имени через системный NSS-механизм, включая возможный /etc/hosts.

dig api.example.com
# Делает DNS-запрос к настроенному для dig серверу.

dig @8.8.8.8 api.example.com
# Отправляет запрос определённому DNS-серверу, не меняя системную конфигурацию.

resolvectl status
# Показывает DNS-конфигурацию на системах с systemd-resolved.
```

**Отличие `getent` от `dig`:** `getent` использует механизм разрешения имён Linux (NSS), который может учитывать `/etc/hosts`; `dig` спрашивает DNS и не полностью повторяет поведение приложений.

Типичные ошибки:

| Сообщение | Значение |
|---|---|
| `NXDOMAIN` | DNS-сервер ответил, что запрошенного имени не существует |
| `SERVFAIL` | DNS-сервер не смог обработать запрос |
| `timed out` / `no servers could be reached` | DNS-клиент не получил ответ вовремя |
| `curl: (6) Could not resolve host` | Приложению не удалось разрешить имя |

Успешный `ping` по IP **не подтверждает**, что DNS работает. Не стоит сразу заменять корпоративный DNS на публичный: могут перестать разрешаться внутренние имена.

## 7. TCP, UDP, порты и адрес прослушивания

**TCP (Transmission Control Protocol)** обеспечивает упорядоченный поток данных с подтверждениями и повторными передачами. **UDP (User Datagram Protocol)** передаёт датаграммы без TCP-механизма установки соединения и гарантий доставки.

Установка TCP-соединения (**Three-Way Handshake**): `SYN → SYN-ACK → ACK`.

**Критически важное различие:** IP-адрес, на котором приложение слушает порт, — это **IP назначения**, а не перечень разрешённых IP клиентов.

| Сокет | Значение |
|---|---|
| `127.0.0.1:8080` | Принимает подключения на loopback-адресе узла |
| `192.168.20.50:8080` | Принимает подключения, направленные на этот IP и порт |
| `0.0.0.0:8080` | Принимает подключения на всех локальных IPv4-адресах сервера |

Клиент из **другой подсети** может обратиться к `192.168.20.50:8080`, если маршрутизация и правила доступа это позволяют. `0.0.0.0` не означает «все адреса одной подсети».

```bash
sudo ss -lntp
# Показывает локальные слушающие TCP-сокеты и использующие их процессы.

sudo ss -lntp 'sport = :8080'
# Показывает локальные TCP-сокеты на порту 8080.

curl -v http://127.0.0.1:8080/health
# Проверяет HTTP endpoint приложения и показывает подробности запроса.

nc -zv -w 3 192.168.20.50 8080
# Дополнительно: пробует установить TCP-соединение с удалённым портом.
```

У `curl`: `-v` — подробный вывод; `-V` — версия; `-c` — сохранение cookies, а не число запросов.

| Результат | Что можно заключить |
|---|---|
| `Connection refused` | TCP-подключение отвергнуто; возможен закрытый порт или активный отказ |
| `Connection timed out` | TCP-подключение не установилось вовремя; причина пока неизвестна |
| `Connected` и HTTP `500` | TCP успешно, приложение ответило ошибкой HTTP |
| HTTP `502 Bad Gateway` | Proxy не получил корректного ответа от upstream-сервиса |

Успешное TCP-подключение к PostgreSQL на `5432` не гарантирует, что пользователь авторизуется или запросы к базе работают.

## 8. Firewalld и зоны

Зона `firewalld` — набор правил для входящего трафика. Зоны могут назначаться интерфейсам и IP-источникам. Предопределённые зоны: `drop`, `block`, `public`, `external`, `dmz`, `work`, `home`, `internal`, `trusted`. Конкретные правила зависят от конфигурации.

```bash
sudo firewall-cmd --get-active-zones
# Показывает активные зоны, интерфейсы и источники.

sudo firewall-cmd --zone=public --list-all
# Показывает настройки зоны public.

sudo firewall-cmd --zone=public --query-port=8080/tcp
# Проверяет, добавлен ли порт 8080/tcp в список портов зоны public.

sudo firewall-cmd --permanent --zone=public --add-port=8080/tcp
# Добавляет постоянное разрешение порта 8080/tcp в указанной зоне.

sudo firewall-cmd --reload
# Применяет постоянную конфигурацию без перезагрузки системы.
```

`--permanent` сохраняет правило, но не применяет его сразу к текущему трафику; обычный `--reload` загружает постоянную конфигурацию и сбрасывает runtime-only изменения.

Разрешение порта в зоне `public` **не означает** автоматического разрешения в `internal`. Результат `--query-port=yes` сам по себе не гарантирует доступность сервиса: возможны другие правила, неправильная зона, проблемы с сервисом или маршрутом.

## 9. Методика troubleshooting

1. Зафиксировать **симптом** (время, IP, порт, точный текст ошибки).
2. Проверить состояние приложения и прослушиваемый сокет.
3. Проверить IP-адреса интерфейсов и маршрут.
4. Если используется имя, проверить DNS отдельно.
5. Проверить нужную зону firewall и политику доступа.
6. Сопоставить ошибку TCP/HTTP с журналами приложения.
7. Сформулировать гипотезу и подтвердить её, **не меняя настройки вслепую**.
8. Выполнить минимальное согласованное исправление и повторить исходный запрос.

```bash
systemctl status backend-api.service
# Показывает состояние backend-службы.

journalctl -u backend-api.service -n 50 --no-pager
# Показывает последние 50 сообщений службы.

ping -c 4 192.168.20.50
# Отправляет четыре ICMP-запроса; это не тест доступности TCP-порта.
```

`tcpdump` — дополнительный инструмент наблюдения за пакетами. Детальный пакетный анализ и сложная асимметричная маршрутизация пока вне обязательного минимума.

> **Diagnose → Hypothesis → Verify Root Cause → Minimal Fix → Recheck.**
