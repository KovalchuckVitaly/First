# Module 05 — Linux Networking
## Practice & Troubleshooting

Все ситуации ниже — **учебные сценарии**, разобранные на занятиях. Примеры вывода иллюстративны: это не отчёт о выполненных изменениях на production-серверах.

## 1. Базовые диагностические команды

```bash
ip -br addr
# Интерфейсы, их состояния и IP-адреса.

ip route show
# Маршруты, известные Linux.

ip route get 8.8.8.8
# Какой маршрут ядро выберет к 8.8.8.8.

ip neigh show
# Таблица соседей и ARP-состояния.

ping -c 4 192.168.0.200
# Четыре ICMP-запроса для проверки отклика IP-адреса.

sudo ss -lntp 'sport = :8080'
# Проверка локального сокета, слушающего TCP-порт 8080.

curl -v http://127.0.0.1:8080/health
# Подробная проверка локального HTTP endpoint.

dig api.example.com
# Запрос DNS-записи через настроенный резолвер.

dig @8.8.8.8 api.example.com
# Тот же DNS-запрос через выбранный DNS-сервер.

nc -zv -w 3 192.168.0.200 5432
# Дополнительный инструмент: TCP-подключение к удалённой БД.
```

## 2. Case №1 — Payments API не подключается к PostgreSQL

**Симптом:** локальный запрос к Payments API возвращает:

```text
* Connected to 127.0.0.1 port 8080
HTTP/1.1 500 Internal Server Error
{"error":"Database connection failed"}
```

**Вывод:** TCP-подключение к API работает. Проблема проявляется на уровне приложения/его зависимости.

```bash
journalctl -u payments-api.service -n 50 --no-pager
# Проверяем сообщения приложения о причине HTTP 500.
```

```text
ERROR: Connection to 192.168.0.200:5432 timed out
```

Проверяем хост БД и порт отдельно:

```bash
ping -c 4 192.168.0.200
# Есть ли ICMP-ответы от сервера PostgreSQL?

nc -zv -w 3 192.168.0.200 5432
# Устанавливается ли TCP-соединение с портом PostgreSQL?
```

В учебном варианте `ping` успешен, а `nc` возвращает `Connection refused`.

На сервере **PostgreSQL**:

```bash
sudo ss -lntp 'sport = :5432'
# Проверяем, на каких IP-адресах слушает PostgreSQL.
```

```text
LISTEN 127.0.0.1:5432
```

**Причина в этой учебной ветке:** PostgreSQL привязан к loopback и не слушает сетевой IP `192.168.0.200`.

После разрешённого изменения адреса прослушивания и проверки firewall появляется другая ошибка:

```text
FATAL: no pg_hba.conf entry for host "192.168.0.181",
user "payments", database "payments_db"
```

Это уже **отказ PostgreSQL по правилам доступа**, а не проблема установления TCP. Не добавлять клиентов в `pg_hba.conf` без проверки политики безопасности.

## 3. Case №2 — сервис слушает, но порт закрыт в нужной зоне

**Симптом:** клиент получает `Connection timed out` при обращении к `192.168.10.50:8080`.

```bash
sudo ss -lntp 'sport = :8080'
# Проверяем локальный адрес и порт приложения.
```

Если вывод — `127.0.0.1:8080`, удалённый клиент не попадёт на `192.168.10.50:8080`. Если вывод — `0.0.0.0:8080`, приложение слушает все локальные IPv4-адреса; проверяем следующую причину.

```bash
ip -br addr
# Проверяем, назначен ли IP 192.168.10.50 сетевому интерфейсу.

sudo firewall-cmd --get-active-zones
# Проверяем, к какой зоне относится нужный интерфейс.

sudo firewall-cmd --zone=public --query-port=8080/tcp
# Проверяем список разрешённых портов зоны public.
```

Условие: `ens33` = `192.168.10.50`, зона `public`, команда `--query-port` вернула `no`. Политика доступа согласована.

```bash
sudo firewall-cmd --permanent --zone=public --add-port=8080/tcp
# Сохраняем разрешение TCP 8080 в постоянной конфигурации.

sudo firewall-cmd --reload
# Применяем постоянную конфигурацию к действующему firewall.
```

**Обязательный последний шаг:** повторить исходный `curl` с компьютера клиента. Возврат `success` от firewall — не проверка доступности приложения.

## 4. Case №3 — DNS timeout при работающей IP-связи

```text
curl: (6) Could not resolve host: api.example.com
```

```bash
dig api.example.com
# Пробуем разрешить имя через DNS по умолчанию.

cat /etc/resolv.conf
# Проверяем настройки резолвера Linux.

dig @8.8.8.8 api.example.com
# Сравниваем результат с другим DNS-сервером.
```

Учебный результат:

```text
;; communications error to 192.168.1.1#53: timed out
;; no servers could be reached
```

Но при обращении к `8.8.8.8`:

```text
status: NOERROR
api.example.com. 300 IN A 203.0.113.25
```

**Вывод:** альтернативный DNS отвечает, а штатный `192.168.1.1` — нет. Это **не доказывает**, что сервер `192.168.1.1` сломан: запрос или ответ могли блокироваться. Не менять DNS-клиент вслепую, если он обслуживает внутренние домены.

## 5. Case №4 — HTTP 502 после деплоя: EADDRINUSE

Схема: Nginx → `127.0.0.1:3000` → Backend API. После деплоя пользователь получает `502 Bad Gateway`.

```bash
systemctl status nginx.service
# Проверяем состояние reverse proxy.

systemctl status backend-api.service
# Проверяем состояние backend-сервиса.

journalctl -u backend-api.service -n 50 --no-pager
# Проверяем журнал приложения.
```

```text
Error: listen EADDRINUSE: address already in use 127.0.0.1:3000
```

`EADDRINUSE` означает, что адрес и порт уже используются несовместимым сокетом.

```bash
sudo ss -lntp 'sport = :3000'
# Ищем процесс, занявший порт.

ps -p 1820 -f
# Изучаем владельца и команду запуска процесса с PID 1820.

sudo systemctl status 1820
# Проверяем, к какому systemd unit/cgroup относится процесс.
```

Установлено: порт занимает `backend-legacy.service`. **Нельзя автоматически делать `kill 1820`**: процесс может автоматически перезапуститься, а служба — понадобиться другому приложению.

После подтверждения администратора, что старый сервис больше не нужен:

```bash
sudo systemctl disable --now backend-legacy.service
# Останавливаем старую службу и отключаем её автозапуск.

sudo systemctl restart backend-api.service
# Запускаем актуальный backend.

systemctl status backend-api.service
# Проверяем статус после запуска.

curl -v http://127.0.0.1:3000/health
# Проверяем ответ актуального backend по HTTP.
```

Далее нужно повторить запрос через Nginx, чтобы убедиться, что внешний `502` исчез.

## 6. Case №5 — асимметричная маршрутизация: причина не доказана

**Клиент:** `192.168.10.25`.

**Backend API:** `192.168.20.50:8080`.

**На сервере:** `ens33 = 192.168.20.50/24`, `ens34 = 10.0.0.50/24`, приложение слушает `0.0.0.0:8080`.

```bash
ip route get 192.168.10.25 from 192.168.20.50
# Проверяем маршрут ответных пакетов с исходным адресом приложения.
```

```text
192.168.10.25 from 192.168.20.50 via 10.0.0.1 dev ens34
```

В демонстрационной части анализа пакетов мы увидели:

- SYN от клиента поступают на сервер через `ens33`.
- SYN-ACK выходят через `ens34`.
- На клиенте SYN-ACK **не появляются**, соединение не устанавливается.

**Что подтверждено:** проблема находится где-то на обратном пути между выходом сервера и клиентом.

**Что не подтверждено:** какая именно настройка на маршрутизаторе, firewall или следующем узле вызвала потерю пакетов. Асимметричный путь сам по себе не равен неисправности.

`tcpdump` использовался как **дополнительный демонстрационный инструмент**, а не как обязательная для запоминания команда текущего уровня.

## 7. Чек-лист действий Junior DevOps

1. Записать точный адрес, порт, ошибку и момент начала проблемы.
2. Проверить приложение и его локальный сокет.
3. Проверить IP-адреса интерфейсов.
4. Проверить маршруты к получателю и обратно к клиенту.
5. Если есть домен — проверить DNS.
6. Проверить зону `firewalld` и разрешения.
7. Разделить ошибки TCP, HTTP и приложения.
8. Сформулировать гипотезу, **подтвердить её**, внести минимальное исправление.
9. Повторить исходную проверку и убедиться, что проблема исчезла.

> Не путать «подозрительный маршрут» с доказанной первопричиной.
