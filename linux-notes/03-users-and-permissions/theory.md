# Module 03 — Users and Permissions

## 1. Linux permissions

В Linux права доступа определяют, кто и какие действия может выполнять с файлами и директориями.

Основные права:

| Право | Число | Для файла | Для директории |
|---|---:|---|---|
| `r` | 4 | читать содержимое | видеть список имён внутри директории |
| `w` | 2 | изменять содержимое | создавать, удалять и переименовывать объекты |
| `x` | 1 | выполнять файл | заходить в директорию и обращаться к объектам внутри |

Права разделены на три класса:

- `u` — owner (владелец)
- `g` — group (группа)
- `o` — others (остальные)

Пример:

```bash
ls -l file.txt
# Показывает владельца, группу и права доступа к файлу.
```

Результат:

```text
-rw-r----- 1 alice developers 1024 file.txt
```

Разбор:

```text
rw-  → owner
r--  → group
---  → others
```

Числовая запись:

```text
rw- = 4 + 2 = 6
r-- = 4
--- = 0

640
```

Изменение прав:

```bash
chmod 640 file.txt
# Устанавливает owner=rw, group=r, others=нет прав.
```

```bash
chmod g+w file.txt
# Добавляет группе право записи в файл.
```

---

## 2. Как Linux выбирает права пользователя

Linux не объединяет права owner, group и others.

Проверка идёт последовательно:

1. UID пользователя совпадает с UID владельца файла → используются только owner permissions.
2. Пользователь подходит под группу файла → используются group permissions.
3. Иначе используются others permissions.

Если пользователь является владельцем файла, но у owner нет нужного права, Linux не пытается взять более широкие права из group или others.

---

## 3. Права директорий

Права директорий имеют другой смысл, чем права обычных файлов.

### `r` — read

Позволяет получить список имён объектов внутри директории.

### `w` — write

Позволяет изменять содержимое самой директории:

- создавать файлы;
- удалять файлы;
- переименовывать файлы.

### `x` — execute/search

Позволяет проходить через директорию и обращаться к объектам внутри неё.

Например, чтобы открыть:

```text
/opt/app/config/settings.conf
```

нужно иметь `x` на:

```text
/opt
/opt/app
/opt/app/config
```

Для диагностики удобно использовать:

```bash
namei -l /opt/app/config/settings.conf
# Разбирает полный путь и показывает права каждого компонента пути.
```

### Важный момент: удаление файла

Право `w` на самом файле не определяет возможность его удаления.

Удаление файла является изменением содержимого родительской директории.

Поэтому для удаления обычно нужны `w+x` на директорию.

## 4. Владельцы файлов

Каждый файл имеет:

- UID владельца;
- GID группы.

Изменение владельца:

```bash
sudo chown deploy file.txt
# Меняет владельца файла на пользователя deploy.
```

Изменение владельца и группы:

```bash
sudo chown deploy:developers file.txt
# Меняет владельца на deploy, а группу на developers.
```

Изменение только группы:

```bash
sudo chgrp developers file.txt
# Меняет группу файла на developers.
```

## 5. umask

`umask` определяет, какие права будут убраны при создании новых файлов и директорий.

Проверить текущую маску:

```bash
umask
# Показывает текущую umask процесса shell.
```

Обычно программы запрашивают максимум:

```text
файл:      666
директория: 777
```

При:

```text
umask 022
```

обычно получаем:

```text
файл:      644
директория: 755
```

При:

```text
umask 002
```

обычно:

```text
файл:      664
директория: 775
```

Важно: `umask` не устанавливает права напрямую. Она удаляет определённые биты из прав, которые запросила программа при создании объекта.

Также `umask` является состоянием процесса и наследуется дочерними процессами.

## 6. SUID

SUID используется для исполняемых файлов.

Если executable имеет SUID, процесс запускается с effective UID владельца файла.

Пример:

```bash
ls -l /usr/bin/passwd
# Показывает права executable passwd; на системах с SUID увидим s в owner execute.
```

Пример отображения:

```text
-rwsr-xr-x
```

`s` на месте owner `x` означает:

```text
SUID + execute
```

Установка:

```bash
sudo chmod u+s program
# Добавляет SUID исполняемому файлу.
```

Числовое представление special bit:

```text
SUID = 4
```

Например:

```bash
sudo chmod 4755 program
# 4 включает SUID, а 755 задаёт обычные права.
```

SUID не означает, что пользователь получает право редактировать файл. Он влияет на effective UID процесса при выполнении программы.

---

## 7. SGID

Для исполняемого файла SGID заставляет процесс получить effective GID группы файла.

Для директорий SGID имеет особенно полезное назначение:

**новые объекты наследуют группу родительской директории.**

Пример:

```bash
sudo chmod g+s /srv/project
# Устанавливает SGID на директорию.
# Новые объекты внутри будут наследовать группу /srv/project.
```

Числовое значение:

```text
SGID = 2
```

Например:

```bash
sudo chmod 2775 /srv/project
# 2 включает SGID, 775 задаёт обычные права директории.
```

Важно: SGID наследует **группу**, но сам по себе не гарантирует группе право записи в новые файлы.

Например, при `umask 022` новый файл может получить:

```text
644
```

и группа не сможет его редактировать.

## 8. Sticky bit

Sticky bit обычно используется на общих writable-директориях.

Пример:

```text
/tmp
```

Проверка:

```bash
ls -ld /tmp
# Показывает права директории /tmp и позволяет увидеть sticky bit.
```

Типичный результат:

```text
drwxrwxrwt
```

`t` означает sticky bit.

Несмотря на то что пользователи могут создавать файлы в такой директории, sticky bit ограничивает удаление и переименование чужих файлов.

Числовое значение:

```text
Sticky = 1
```

Например:

```bash
sudo chmod 1777 /shared
# Устанавливает sticky bit и права rwxrwxrwx.
```

Special bits:

```text
SUID   = 4
SGID   = 2
Sticky = 1
```

# ACL

## 9. Зачем нужен ACL

Стандартные permissions позволяют задать права только для:

```text
owner
group
others
```

ACL позволяет назначить дополнительные права конкретным пользователям и группам.

Например, дать пользователю `bob` доступ к файлу, не меняя владельца или основную группу файла.

Посмотреть ACL:

```bash
getfacl file.txt
# Показывает стандартные и дополнительные ACL-записи файла.
```

Добавить ACL для пользователя:

```bash
setfacl -m u:bob:rw file.txt
# Даёт пользователю bob права read и write через ACL.
```

Добавить ACL для группы:

```bash
setfacl -m g:developers:rw file.txt
# Даёт группе developers права read и write через ACL.
```

Удалить ACL конкретного пользователя:

```bash
setfacl -x u:bob file.txt
# Удаляет ACL-запись пользователя bob.
```

---

## 10. ACL mask

ACL mask ограничивает максимальные эффективные права:

- named users;
- owning group;
- named groups.

Пример:

```text
user:bob:rw-
mask::r--
```

Эффективные права Bob:

```text
r--
```

Потому что mask запрещает `w`.

`getfacl` может показать:

```text
user:bob:rw-        #effective:r--
```

Изменение mask:

```bash
setfacl -m m::rw file.txt
# Разрешает ACL-классу максимум read + write.
```

Важно: обычный `chmod` на объекте с extended ACL может изменить ACL mask, поэтому после изменения permissions ACL нужно проверять повторно.

---

## 11. Default ACL

Default ACL применяется к директориям и служит шаблоном для новых объектов внутри них.

Например:

```bash
sudo setfacl -m d:g:developers:rwx /srv/project
# Устанавливает default ACL для группы developers.
# Новые объекты внутри /srv/project будут получать соответствующую ACL-запись.
```

Посмотреть ACL директории:

```bash
getfacl /srv/project
# Показывает Access ACL и, если настроен, Default ACL директории.
```

Важно:

**Default ACL не предоставляет доступ к самой директории.**

Он влияет на ACL новых объектов.

Также default ACL не может добавить права, которые программа вообще не запросила при создании объекта. Например, обычный текстовый файл обычно не получает execute автоматически.

Для shared directory часто используется комбинация:

```text
SGID        → наследование group ownership
Default ACL → наследование permissions
```

# Users and Groups

## 12. UID и GID

Linux внутри системы работает не с именами пользователей, а с числовыми идентификаторами:

```text
UID → User ID
GID → Group ID
```

Имя пользователя — удобное отображение UID для человека.

Посмотреть информацию о пользователе:

```bash
id deploy
# Показывает UID, primary GID и supplementary groups пользователя deploy.
```

---

## 13. /etc/passwd

Информация об аккаунтах хранится в `/etc/passwd`.

Получить запись через NSS:

```bash
getent passwd deploy
# Получает запись пользователя deploy через настроенные NSS-источники.
```

Пример:

```text
deploy:x:1006:1005::/home/deploy:/bin/bash
```

Поля:

```text
username
password placeholder
UID
primary GID
GECOS
home directory
login shell
```

`getent` предпочтительнее прямого `grep /etc/passwd`, когда нужно учитывать NSS и потенциально внешние источники пользователей.

---

## 14. /etc/shadow

Хэши паролей и password-aging информация находятся в:

```text
/etc/shadow
```

Обычные пользователи не должны иметь возможность читать его содержимое.

Посмотреть password aging:

```bash
sudo chage -l deploy
# Показывает параметры срока действия пароля и аккаунта deploy.
```

Принудительно потребовать смену пароля:

```bash
sudo chage -d 0 deploy
# Устанавливает дату последней смены пароля так,
# чтобы пользователь сменил пароль при следующем входе.
```

---

## 15. /etc/group

Информация о группах хранится в `/etc/group`.

Получить информацию:

```bash
getent group developers
# Получает информацию о группе developers через NSS.
```

Primary group пользователя может не отображаться в списке участников `/etc/group`.

Поэтому для проверки членства пользователя удобнее:

```bash
id deploy
# Показывает primary и supplementary groups пользователя.
```

---

## 16. Создание пользователя

Пример:

```bash
sudo useradd -m -s /bin/bash deploy
# Создаёт пользователя deploy.
# -m создаёт домашнюю директорию.
# -s задаёт login shell.
```

Назначить primary group:

```bash
sudo usermod -g developers deploy
# Меняет primary group пользователя deploy на developers.
```

Добавить supplementary group:

```bash
sudo usermod -aG docker deploy
# -G задаёт supplementary groups.
# -a означает append — добавить группу, не удаляя существующие.
```

Критически важно:

```bash
sudo usermod -G monitoring deploy
# ОПАСНЫЙ пример: без -a список supplementary groups заменяется.
# Пользователь может потерять членство в остальных дополнительных группах.
```

---

## 17. /etc/skel

`/etc/skel` содержит шаблон файлов для новых домашних директорий.

При создании пользователя с home содержимое `/etc/skel` обычно копируется в его домашнюю директорию.

Например:

```bash
ls -la /etc/skel
# Показывает шаблонные файлы для новых home directories.
```

---

## 18. Блокировка аккаунта

Заблокировать пароль:

```bash
sudo passwd -l deploy
# Блокирует password authentication для deploy,
# изменяя соответствующее password-поле.
```

Разблокировать:

```bash
sudo passwd -u deploy
# Снимает блокировку password authentication.
```

Важно:

**блокировка пароля не обязательно блокирует SSH key authentication.**

Если необходимо запретить интерактивный login, одним из вариантов является shell:

```text
/usr/sbin/nologin
```

Но `nologin` не означает, что процессы вообще нельзя запускать от имени этого UID.

Например:

```bash
sudo -u myapp id
# Запускает команду id от имени myapp.
# Может работать даже если login shell пользователя — nologin.
```

---

## 19. System accounts

System account — это обычный с точки зрения ядра UID, обычно предназначенный для запуска сервисов.

Создание:

```bash
sudo useradd -r -M -s /usr/sbin/nologin myapp
# -r создаёт system account.
# -M не создаёт home directory.
# -s задаёт shell nologin.
```

У такого пользователя может быть запись home directory в `/etc/passwd`, даже если физически директория не существует.

Для данных приложения лучше создать отдельную директорию:

```bash
sudo mkdir /var/lib/myapp
# Создаёт каталог для данных приложения.
```

```bash
sudo chown myapp:myapp /var/lib/myapp
# Передаёт каталог системному пользователю и его группе.
```

```bash
sudo chmod 700 /var/lib/myapp
# Разрешает полный доступ только владельцу myapp.
```

## 20. Изменение групп и активные процессы

Если удалить пользователя из supplementary group, уже запущенный shell может продолжать видеть старую группу.

Причина: credentials процесса были получены при создании login session.

Например, после изменения:

```bash
id deploy
# Проверяет актуальное членство deploy согласно системным источникам.
```

Но команда `id` внутри старой пользовательской сессии может ещё показывать старый набор групп.

Новая login session получает обновлённые credentials.

# User Offboarding

## 21. Почему нельзя просто выполнить userdel

Перед удалением пользователя нужно проверить файлы, которыми он владеет.

Поиск:

```bash
sudo find / -user alex 2>/dev/null
# Ищет файлы, владельцем которых является alex.
# Ошибки доступа перенаправляются в /dev/null.
```

Если важный файл нужно сохранить:

```bash
sudo chown deploy:developers /var/www/project/file1.txt
# Передаёт важный проектный файл другому владельцу и группе.
```

После проверки можно удалить пользователя:

```bash
sudo userdel -r alex
# Удаляет аккаунт alex и пытается удалить его home directory и mail spool.
```

`userdel -r` не гарантирует удаление всех файлов пользователя по всей файловой системе.

## 22. Orphaned UID/GID

Файловая система хранит числовые UID/GID, а не имена пользователей и групп.

Поэтому после удаления пользователя файл может остаться с числовым UID.

Проверка:

```bash
sudo find / -uid 1002 2>/dev/null
# Ищет файлы, у которых owner UID равен 1002.
```

Для группы:

```bash
sudo find / -gid 1003 2>/dev/null
# Ищет файлы, у которых group GID равен 1003.
```

Это особенно важно перед повторным использованием UID/GID: новый пользователь с тем же UID автоматически будет восприниматься системой как владелец старых файлов.

## 23. Диагностика Permission denied

При ошибке:

```text
Permission denied
```

не нужно сразу выполнять `chmod 777`.

Правильный подход:

```text
1. Определить пользователя процесса.
2. Проверить UID/GID и группы.
3. Проверить владельца файла.
4. Проверить обычные permissions.
5. Проверить права всех директорий в пути.
6. Проверить ACL и ACL mask.
7. Проверить special bits, если они имеют отношение к ситуации.
8. Только после определения root cause вносить минимальное изменение.
9. Проверить результат от имени реального пользователя/сервиса.
```

Полезные команды:

```bash
id username
# Показывает UID/GID и группы пользователя.
```

```bash
namei -l /path/to/file
# Показывает права каждого компонента полного пути.
```

```bash
getfacl /path/to/file
# Показывает ACL и ACL mask объекта.
```

```bash
stat /path/to/file
# Показывает подробные метаданные файла, включая UID/GID и permissions.
```

```bash
sudo -u username cat /path/to/file
# Проверяет реальный доступ к файлу от имени нужного пользователя.
```

Главный принцип администратора:

> Сначала диагностика → затем подтверждение причины → минимальное исправление → проверка результата.
