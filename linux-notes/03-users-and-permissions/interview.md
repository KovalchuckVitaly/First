# Module 03 — Interview Questions

Вопросы для подготовки к техническому собеседованию по Linux permissions, ACL, users и groups.

---

## 1. Что означают r, w и x для обычного файла?

- `r` — прочитать содержимое файла.
- `w` — изменить содержимое файла.
- `x` — выполнить файл как программу/скрипт, если формат файла и система это позволяют.

---

## 2. Что означают r, w и x для директории?

- `r` — получить список имён объектов внутри директории.
- `w` — изменять содержимое директории: создавать, удалять и переименовывать объекты.
- `x` — проходить через директорию и обращаться к объектам внутри неё.

Для доступа к файлу по полному пути нужен `x` на каждом компоненте пути.

---

## 3. Какие права нужны для удаления файла?

Обычно нужны:

```text
w + x
```

на родительскую директорию.

Право `w` на самом файле для его удаления не требуется.

Удаление файла является изменением содержимого директории.

Sticky bit и другие механизмы безопасности могут дополнительно ограничивать удаление.

---

## 4. Пользователь является владельцем файла, но owner permissions запрещают чтение. Group permissions разрешают чтение. Сможет ли он прочитать файл?

Нет.

Linux выбирает один класс permissions:

```text
owner → если UID совпадает
group → если пользователь подходит под group class
others → иначе
```

Если пользователь является owner, используются только owner permissions.

Linux не пытается использовать более широкие права group или others.

---

## 5. Что означает chmod 640 file.txt?

```text
owner:  rw- = 6
group:  r-- = 4
others: --- = 0
```

Владелец может читать и изменять файл.

Группа может только читать.

Остальные не имеют доступа.

---

## 6. Чем отличаются chmod, chown и chgrp?

`chmod` изменяет permissions.

```bash
chmod 640 file.txt
# Устанавливает permissions файла.
```

`chown` изменяет владельца и при необходимости группу.

```bash
sudo chown deploy:developers file.txt
# Меняет owner на deploy и group на developers.
```

`chgrp` изменяет только группу.

```bash
sudo chgrp developers file.txt
# Меняет group ownership файла.
```

---

## 7. Что такое umask?

`umask` определяет, какие permission bits будут убраны из прав, запрошенных программой при создании нового объекта.

Типичные максимальные права:

```text
files:       666
directories: 777
```

При:

```text
umask 022
```

обычно получаем:

```text
files:       644
directories: 755
```

Важно: `umask` не назначает права напрямую. Она ограничивает права, которые запросила создающая объект программа.

---

## 8. Почему новый файл обычно не получает execute permission даже при umask 000?

Потому что обычная программа при создании файла обычно запрашивает:

```text
666
```

То есть execute bits изначально не запрошены.

`umask` может только убрать запрошенные биты, но не добавить отсутствующие.

---

## 9. Что такое SUID?

SUID — special permission bit для executable.

При запуске такого файла процесс получает effective UID владельца executable.

Числовое значение:

```text
SUID = 4
```

Например:

```text
4755
```

означает SUID + обычные permissions `755`.

---

## 10. Что такое SGID?

Для executable SGID влияет на effective GID процесса.

Для директории SGID означает, что новые объекты внутри неё наследуют group ownership родительской директории.

Это часто используется для shared directories.

Числовое значение:

```text
SGID = 2
```

---

## 11. Гарантирует ли SGID, что группа сможет редактировать новые файлы?

Нет.

SGID отвечает за наследование группы, а не за выдачу group write permission.

Например, при `umask 022` новый файл может получить:

```text
644
```

Группа файла будет правильной, но права записи у группы не будет.

Для решения можно использовать подходящую `umask` или Default ACL.

---

## 12. Что такое sticky bit?

Sticky bit используется преимущественно на shared writable directories.

Он ограничивает удаление и переименование чужих файлов.

Классический пример:

```text
/tmp
```

Типичные permissions:

```text
drwxrwxrwt
```

Числовое значение:

```text
Sticky = 1
```

---

## 13. Для чего нужен ACL?

Стандартная Unix permission model предоставляет права для:

```text
owner
group
others
```

ACL позволяет назначить дополнительные права конкретным пользователям или группам без изменения owner/group объекта.

---

## 14. Как посмотреть ACL файла?

```bash
getfacl file.txt
# Показывает Access ACL, mask и другие ACL-записи объекта.
```

---

## 15. Что такое ACL mask?

ACL mask задаёт максимальные эффективные права для ACL-класса, в который входят:

- named users;
- owning group;
- named groups.

Например:

```text
user:bob:rw-
mask::r--
```

Bob фактически получает:

```text
r--
```

Несмотря на ACL entry `rw-`.

---

## 16. Может ли chmod повлиять на ACL?

Да.

На файле с extended ACL изменение group-class permissions через `chmod` может изменить ACL mask.

Поэтому после `chmod` ACL следует проверить:

```bash
getfacl file.txt
# Проверяем ACL и effective permissions после chmod.
```

---

## 17. Чем Access ACL отличается от Default ACL?

Access ACL определяет доступ к существующему объекту.

Default ACL существует на директории и используется как шаблон ACL для новых объектов внутри неё.

Default ACL не предоставляет доступ к самой родительской директории.

---

## 18. Как организовать shared directory для команды?

Один из вариантов:

```text
общая группа
+
SGID directory
+
Default ACL
```

SGID обеспечивает наследование group ownership.

Default ACL обеспечивает наследование нужных permissions.

---

## 19. Что такое UID и GID?

`UID` — числовой идентификатор пользователя.

`GID` — числовой идентификатор группы.

Linux kernel использует именно числовые UID/GID.

Username и group name являются человекочитаемым отображением этих идентификаторов.

---

## 20. Где хранится информация о локальных пользователях?

Основная информация об аккаунтах:

```text
/etc/passwd
```

Password hashes и password-aging информация:

```text
/etc/shadow
```

Информация о локальных группах:

```text
/etc/group
```

При этом система может получать пользователей и группы не только из локальных файлов, поэтому для запросов удобно использовать `getent`.

---

## 21. Какие поля содержит /etc/passwd?

Типичная запись:

```text
deploy:x:1006:1005::/home/deploy:/bin/bash
```

Поля:

```text
username
password placeholder
UID
primary GID
GECOS
home directory
login shell
```

---

## 22. Для чего нужен /etc/shadow?

`/etc/shadow` хранит:

- password hashes;
- дату последней смены пароля;
- password aging;
- expiration-related параметры.

Он защищён от чтения обычными пользователями.

---

## 23. Что такое primary и supplementary groups?

У пользователя есть одна primary group.

Дополнительно он может состоять в нескольких supplementary groups.

Проверить:

```bash
id username
# Показывает UID, primary GID и supplementary groups пользователя.
```

---

## 24. В чём разница между usermod -G и usermod -aG?

```bash
sudo usermod -G monitoring deploy
# ЗАМЕНЯЕТ список supplementary groups пользователя.
```

```bash
sudo usermod -aG monitoring deploy
# ДОБАВЛЯЕТ monitoring к существующим supplementary groups.
```

Использование `-G` без `-a` может случайно удалить пользователя из других дополнительных групп.

---

## 25. Почему после добавления пользователя в группу его старый shell может не видеть новую группу?

Group credentials назначаются процессу при создании login session.

Изменение системной базы пользователей не переписывает credentials уже запущенных процессов.

Поэтому новая login session получает обновлённый список групп, а старый shell может продолжать использовать старый.

---

## 26. Что делает /etc/skel?

`/etc/skel` содержит шаблон файлов и директорий для новых home directories.

При создании пользователя с домашней директорией содержимое `/etc/skel` обычно копируется в его home.

---

## 27. Что делает passwd -l?

```bash
sudo passwd -l deploy
# Блокирует password authentication пользователя deploy.
```

Это не обязательно блокирует другие способы аутентификации, например SSH public key authentication.

---

## 28. Что делает /usr/sbin/nologin?

`nologin` используется как login shell для аккаунтов, которым не нужен обычный интерактивный login.

Например, service accounts.

Но это не запрещает системе запускать процессы с UID такого пользователя.

Пример:

```bash
sudo -u myapp id
# Запускает id от имени myapp даже при shell /usr/sbin/nologin.
```

---

## 29. Что такое system account?

С точки зрения Linux kernel это обычный UID.

Разница в назначении и способе создания.

System accounts обычно используются сервисами и часто имеют:

- UID из системного диапазона;
- отсутствие обычного home;
- shell `nologin`;
- минимально необходимые permissions.

---

## 30. Что произойдёт с файлами после удаления их владельца?

Файлы не обязаны удаляться вместе с аккаунтом.

Inode продолжает хранить числовой UID владельца.

Если username для этого UID больше не существует, инструменты могут показывать числовой UID.

Такой файл может стать orphaned с точки зрения управления аккаунтами.

---

## 31. Чем опасно повторное использование UID?

Допустим, старый пользователь имел:

```text
UID 1002
```

После его удаления на сервере остались файлы с UID `1002`.

Если новому пользователю позже назначить тот же UID, Linux будет считать его владельцем этих файлов.

Поэтому перед удалением пользователя и повторным использованием UID необходимо проверять оставшиеся файлы.

---

## 32. Как найти все файлы пользователя?

До удаления аккаунта:

```bash
sudo find / -user alex 2>/dev/null
# Ищет объекты, владельцем которых является пользователь alex.
```

По числовому UID:

```bash
sudo find / -uid 1002 2>/dev/null
# Ищет объекты с owner UID 1002.
# Полезно в том числе после удаления username.
```

---

## 33. Удаляет ли userdel -r абсолютно все файлы пользователя?

Нет.

```bash
sudo userdel -r alex
# Удаляет аккаунт и пытается удалить его home directory и mail spool.
```

Файлы пользователя в других частях файловой системы могут остаться.

Поэтому перед offboarding нужно искать принадлежащие пользователю файлы отдельно.

---

## 34. Пользователь входит в правильную группу, файл имеет group read, но всё равно получает Permission denied. Что проверять?

Нельзя сразу делать `chmod 777`.

Порядок диагностики:

```text
1. Проверить реального пользователя процесса.
2. Проверить UID/GID и supplementary groups.
3. Проверить ownership файла.
4. Проверить permissions файла.
5. Проверить x на каждом компоненте пути.
6. Проверить ACL.
7. Проверить ACL mask.
8. Проверить дополнительные ограничения, если проблема всё ещё не найдена.
9. Найти root cause.
10. Сделать минимальное исправление.
11. Проверить доступ от имени реального пользователя.
```

Полезная команда для пути:

```bash
namei -l /full/path/to/file
# Показывает permissions каждого компонента полного пути.
```

```text
r/w/x для файла
r/w/x для директории
chmod / chown / chgrp
owner → group → others
umask
SUID
SGID
sticky bit
ACL
ACL mask
Default ACL
UID/GID
/etc/passwd

/etc/group
primary/supplementary groups
usermod -G vs -aG
system accounts
nologin

```

Главное — не просто помнить команды, а понимать, почему Linux разрешает или запрещает конкретную операцию.
